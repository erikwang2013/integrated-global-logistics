## 2. बैकएंड आर्किटेक्चर

### 2.1 लेयर्ड डिज़ाइन

| परत | डायरेक्टरी | ज़िम्मेदारी |
|---|------|------|
| रूटिंग | `config/route.php` | URL से कंट्रोलर मैपिंग, मिडलवेयर बाइंडिंग, संस्करण-नियंत्रित रूट |
| मिडलवेयर | `app/middleware/` | अटैक इंटरसेप्शन(SecurityFilter)、रेट लिमिट(RateLimit)、प्रमाणीकरण(JWT)、अनुमति(RBAC)、API संस्करण(ApiVersion) |
| कंट्रोलर | 14: Dashboard/User/Role/Permission/Config/Log/Profile/Export/Import/Upload/Health/Docs (एडमिन साइड) + Captcha/Auth (API v1) | रिक्वेस्ट पैरामीटर सत्यापन, बिज़नेस लॉजिक कॉल, रिस्पॉन्स फॉर्मेटिंग |
| बिज़नेस सेवा | `app/service/` | पुन: प्रयोज्य बिज़नेस लॉजिक (आरक्षित) |
| डेटा मॉडल | `app/model/` | ORM मैपिंग, संबंध, फ़ील्ड एन्क्रिप्शन/डिक्रिप्शन |
| सार्वजनिक उपयोगिताएँ | `app/common/` | Hashids、Snowflake、Encryption सेवाएँ |

### 2.2 रिक्वेस्ट लाइफसाइकल

```
क्लाइंट रिक्वेस्ट
  │
  ▼
webman HTTP Server (workerman)
  │
  ▼
Route मिलान
  │
  ▼
मिडलवेयर चेन:
  Locale ──────────────► Accept-Language / ?lang= भाषा पहचान
  │
  ▼
  SecurityFilter ──────► HTTP मेथड जाँच → 405 (केवल GET/POST/PUT/DELETE/OPTIONS/HEAD)
  │                     XSS/SQL इंजेक्शन/पाथ ट्रैवर्सल/कमांड इंजेक्शन/CSRF अटैक इंटरसेप्शन (403)
  ▼
  RateLimit ───────────► Redis स्लाइडिंग विंडो रेट लिमिट
  │ (विफल होने पर 429 + Retry-After हेडर)
  ▼
  ApiVersion ─────────► API-Version हेडर सत्यापन, $request->apiVersion इंजेक्ट
  │ (विफल होने पर 400)
  ▼
  AdminAuth ──────────► JWT सत्यापन, $request->adminId इंजेक्ट
  │ (विफल होने पर 401)
  ▼
  AdminPermission ────► RBAC अनुमति सत्यापन (Redis 60s कैश)
  │ (विफल होने पर 403)
  ▼
  OperationLog ───────► ऑपरेशन लॉग रिकॉर्डिंग (POST/PUT/DELETE), स्रोत डिवाइस स्वचालित पहचान
  │
  ▼
Controller::method()
  │
  ├─► पैरामीटर सत्यापन (validator)
  ├─► संवेदनशील ऑपरेशन पुष्टि (confirmPassword)
  ├─► decodeId() — hashid → BIGINT
  ├─► Model ऑपरेशन (स्वचालित encryptable एन्क्रिप्शन/डिक्रिप्शन)
  ├─► encodeId() — BIGINT → hashid
  └─► Response JSON
```

### 2.3 ID लाइफसाइकल

```
जनरेशन (Snowflake) → स्टोरेज (MySQL BIGINT) → ट्रांसमिशन (Hashids एन्कोडिंग) → बाहरी (hash स्ट्रिंग)
                                                                    │
                            HashidsService::decode() ←──────────────┘
```

### 2.4 डेटा एन्क्रिप्शन प्रणाली

```
ट्रांसमिशन परत (encryption)     — AES-256-CBC, स्वतंत्र कुंजी
```

### 3.3 प्राथमिक कुंजी मानक

- प्रकार: `BIGINT UNSIGNED NOT NULL`
- विशेषता: **गैर-ऑटोइन्क्रीमेंट**, Snowflake एल्गोरिदम द्वारा एप्लिकेशन परत में जनरेट
- लाभ: वैश्विक अद्वितीय, वितरित-अनुकूल, ट्रेंड-वृद्धिशील इंडेक्स के लिए अनुकूल, बिज़नेस मात्रा उजागर नहीं
- कॉन्फ़िगरेशन: datacenter_id(0-31) + worker_id(0-31), 1024 नोड समवर्ती समर्थित

## 4. API डिज़ाइन

### 4.1 URL मानक

```
सार्वजनिक इंटरफ़ेस:  /api/captcha/{generate|verify}
           /api/auth/{login|register|refresh}

एडमिन साइड:   /admin/{resource}[/{hashid}]
          /admin/export/{excel|pdf}

संसाधन रूट:
  GET    /admin/user          → सूची
  POST   /admin/user          → निर्माण
  GET    /admin/user/{hashid} → विवरण
  PUT    /admin/user/{hashid} → अपडेट
  DELETE /admin/user/{hashid} → डिलीट (पासवर्ड पुष्टि आवश्यक)

सिस्टम कॉन्फ़िगरेशन:  /admin/config[/{hashid}]
ऑपरेशन लॉग:  /admin/log
प्रोफ़ाइल केंद्र:  /admin/profile[/password|/logout]
आयात:     /admin/import/users
अपलोड:     /admin/upload
बैच:     /admin/user/batch/{destroy|status}
दस्तावेज़:     /api/docs     (OpenAPI 3.0)
स्वास्थ्य:     /health
```

### 4.2 API संस्करण नीति

API संस्करण रिक्वेस्ट हेडर द्वारा नियंत्रित होता है, **URL पाथ में नहीं दिखता**:

```http
API-Version: v1
```

| तंत्र | विवरण |
|------|------|
| डिफ़ॉल्ट संस्करण | `API-Version` हेडर नहीं होने पर डिफ़ॉल्ट `v1` |
| सत्यापन | `ApiVersion` मिडलवेयर सत्यापन, असमर्थित संस्करण 400 लौटाता है |
| रूटिंग | `v()` सहायक फ़ंक्शन संस्करण के अनुसार कंट्रोलर क्लास गतिशील रूप से रिज़ॉल्व करता है |
| डायरेक्टरी | कंट्रोलर संस्करण-वार व्यवस्थित: `app/api/{version}/controller/` |

विस्तार उदाहरण — v2 API जोड़ना:
1. `app/api/v2/controller/AuthController.php` बनाएँ
2. `ApiVersion` मिडलवेयर के `SUPPORTED` कॉन्स्टेंट में `'v2'` जोड़ें
3. रूट परिभाषा में संशोधन आवश्यक नहीं

```bash
# v1 उपयोग करें
curl -H "API-Version: v1" /api/auth/login

# v2 उपयोग करें
curl -H "API-Version: v2" /api/auth/login

# न भेजें, डिफ़ॉल्ट v1
curl /api/auth/login
```

### 4.3 रेट लिमिट नीति

Redis Sorted Set स्लाइडिंग विंडो एल्गोरिदम पर आधारित, एटॉमिक Lua स्क्रिप्ट निष्पादन:

| इंटरफ़ेस | सीमा |
|------|------|
| डिफ़ॉल्ट | 60 बार/मिनट/IP/रूट |
| POST /api/auth/login | 10 बार/मिनट |
| POST /api/auth/register | 5 बार/मिनट |

सीमा से अधिक होने पर 429 लौटता है, रिस्पॉन्स हेडर में X-RateLimit-Limit / Remaining / Reset / Retry-After।

### 4.4 एकीकृत रिस्पॉन्स

```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

| code | अर्थ | ट्रिगर परिदृश्य |
|------|------|---------|
| 0 | सफल | सामान्य रिस्पॉन्स |
| 400 | पैरामीटर त्रुटि | रिक्वेस्ट फॉर्मेट सही नहीं |
| 401 | प्रमाणीकरण नहीं | टोकन अनुपस्थित/समाप्त/अमान्य |
| 403 | अनुमति नहीं | उपयोगकर्ता की भूमिका में आवश्यक अनुमति नहीं |
| 404 | मौजूद नहीं | संसाधन नहीं मिला |
| 422 | सत्यापन विफल | फॉर्म पैरामीटर नियमों के अनुरूप नहीं / पासवर्ड पुष्टि विफल |
| 500 | सर्वर त्रुटि | अप्रत्याशित एक्सेप्शन |

### 4.6 अनुमति मॉडल (RBAC)

```
  उपयोगकर्ता ──┬── भूमिका ──┬── अनुमति
  User     Role      Permission
                 │
                 ├── type=1: मेनू (साइडबार दृश्यता नियंत्रित)
                 ├── type=2: बटन (पेज के भीतर ऑपरेशन नियंत्रित)
                 └── type=3: API  (इंटरफ़ेस एक्सेस नियंत्रित)

  अनुमति पहचानकर्ता फॉर्मेट: {method}.{path}
  उदा: get.admin/user  post.admin/user  delete.admin/user
  सुपर एडमिन पहचानकर्ता: * (सभी अनुमति जाँच छोड़ें)
```

### 4.7 संवेदनशील ऑपरेशन पुनः पुष्टि

उपयोगकर्ता, भूमिका, अनुमति हटाने जैसे संवेदनशील ऑपरेशन के लिए रिक्वेस्ट बॉडी में वर्तमान उपयोगकर्ता का पासवर्ड भेजकर पहचान पुनः सत्यापित करनी होती है:

```
क्लाइंट                           सर्वर
  │                                │
  │  DELETE /admin/user/{hashid}  │
  │  { password: "******" }       │
  │────────────────────────────►  │
  │                                │ confirmPassword(adminId, password)
  │                                │ → पासवर्ड गलत होने पर 422
  │                                │ → पासवर्ड सही होने पर आगे बढ़ें
  │◄── 200 { code: 0 }           │
```

फ्रंटएंड डिलीट ऑपरेशन ट्रिगर करने से पहले पुष्टि डायलॉग दिखाता है, उपयोगकर्ता का पासवर्ड एकत्र करके रिक्वेस्ट भेजता है।

## 6. सुरक्षा डिज़ाइन

### 6.1 गहन सुरक्षा

| स्तर | उपाय |
|------|------|
| मेथड सीमा | SecurityFilter HTTP मेथड व्हाइटलिस्ट, केवल GET/POST/PUT/DELETE/OPTIONS/HEAD, गैर-मानक मेथड 405 |
| अटैक इंटरसेप्शन | SecurityFilter मिडलवेयर, XSS/SQL इंजेक्शन/पाथ ट्रैवर्सल/कमांड इंजेक्शन/CSRF पहचान इंटरसेप्शन |
| ह्यूमन-मशीन सत्यापन | क्लिक कैप्चा (Click Captcha), लॉगिन/रजिस्ट्रेशन अनिवार्य सत्यापन |
| खाता लॉक | लगातार 5 बार लॉगिन विफल → 15 मिनट खाता लॉक, लॉक अवधि में 429 |
| सत्र सीमा | एक ही उपयोगकर्ता अधिकतम 3 समवर्ती टोकन, अधिक होने पर सबसे पुराना टोकन स्वचालित ब्लैकलिस्ट |
| रेट लिमिट | RateLimit मिडलवेयर, Redis स्लाइडिंग विंडो, Lua एटॉमिक |
| CSP | Content-Security-Policy हेडर संसाधन स्रोत सीमित, XSS और डेटा इंजेक्शन रोकथाम |
| ऑपरेशन पुष्टि | डिलीट जैसे संवेदनशील ऑपरेशन के लिए वर्तमान उपयोगकर्ता पासवर्ड पुनः पुष्टि आवश्यक |
| ट्रांसमिशन | HTTPS + JWT Bearer Token |
| इंटरफ़ेस ID | Hashids एन्क्रिप्शन, बाहरी रूप से वास्तविक ID अनुमान नहीं लगा सकते |
| रिक्वेस्ट बॉडी | AES-256-CBC संवेदनशील फ़ील्ड एन्क्रिप्शन |
| डेटाबेस | BIGINT प्राथमिक कुंजी (ऑटोइन्क्रीमेंट मात्रा उजागर नहीं) |
| डेटाबेस | AES-128-ECB संवेदनशील फ़ील्ड एन्क्रिप्टेड स्टोरेज |
| प्रमाणीकरण | JWT HS256, 2h समाप्ति + refresh token |
| अनुमति | RBAC, method.path ग्रैन्युलरिटी अनुमति नियंत्रण |
| ऑडिट | OperationLog सभी ऑपरेशन रिकॉर्ड (source स्रोत डिवाइस स्वचालित पहचान सहित) |

### 6.2 कुंजी प्रबंधन

```
JWT_SECRET          → पर्यावरण चर इंजेक्शन, 64-वर्ण रैंडम स्ट्रिंग
HASHIDS_SALT        → अद्वितीय सॉल्ट मान, लीक होने पर वैश्विक बदलाव आवश्यक
ENCRYPTION_KEY      → API ट्रांसमिशन एन्क्रिप्शन कुंजी, 32 बाइट
ENCRYPTABLE_KEY     → DB स्टोरेज एन्क्रिप्शन कुंजी, ट्रांसमिशन कुंजी से स्वतंत्र
SCOUT_HOSTS         → ES पता, आंतरिक नेटवर्क डिप्लॉयमेंट
```

## 8. डिप्लॉयमेंट आर्किटेक्चर

### 8.1 अनुशंसित टोपोलॉजी

```
Nginx (:443 HTTPS) → webman worker × N (:8787) → MySQL + ES + Redis
                    स्टैटिक फ़ाइलें: Flutter Web build/
```

### 8.2 Docker Compose (प्रोडक्शन के लिए अनुशंसित)

प्रोजेक्ट रूट का `docker-compose.yml` उपरोक्त टोपोलॉजी की सभी सेवाओं का ऑर्केस्ट्रेशन करता है:

| सेवा | इमेज/बिल्ड | पोर्ट | विवरण |
|------|----------|------|------|
| `nginx` | nginx:alpine | 80, 443 | रिवर्स प्रॉक्सी + स्टैटिक फ़ाइलें + Gzip |
| `app` | लोकल `Dockerfile` बिल्ड | 8787 | PHP 8.3 + OPcache + webman |
| `mysql` | mysql:8.0 | 3306 | मुख्य डेटाबेस, डेटा वॉल्यूम पर्सिस्टेंस |
| `redis` | redis:7-alpine | 6379 | कैश / रेट लिमिट / कैप्चा |
| `elasticsearch` | elasticsearch:8.x | 9200 | फुल-टेक्स्ट सर्च |

शुरू करने से पहले `docker-compose.yml` में `JWT_SECRET`、`HASHIDS_SALT`、`ENCRYPTION_KEY` जैसी कुंजियों को रैंडम स्ट्रिंग से बदलें।

```bash
cp .env.docker .env
docker-compose up -d
```

### 8.3 CI/CD

GitHub Actions निरंतर इंटीग्रेशन `.github/workflows/ci.yml` में परिभाषित:
- PHP सिंटैक्स जाँच (`php -l`)
- PHPUnit यूनिट टेस्ट
- Flutter स्टैटिक विश्लेषण (`flutter analyze`)

### 8.4 डेटाबेस बैकअप

`database/backup/backup.sh` — mysqldump + gzip बैकअप, 30 दिन पुराने बैकअप स्वचालित सफाई।
`database/backup/restore.sh` — इंटरैक्टिव बैकअप चयन और रिस्टोर।

### 8.5 मॉनिटरिंग

`GET /metrics` एंडपॉइंट (`MetricsController`) Prometheus text format में 5 gauge मेट्रिक्स उजागर करता है: HTTP रिक्वेस्ट कुल संख्या, सक्रिय उपयोगकर्ता संख्या, डेटाबेस/Redis कनेक्शन स्थिति, मेमोरी उपयोग।
