## 1. Обзор эшелонированной обороны

Система использует 7-уровневую модель эшелонированной обороны: вредоносные запросы фильтруются снаружи внутрь, слой за слоем, так что при отказе любого отдельного уровня остаются резервные линии защиты.

Вся цепочка промежуточного ПО выполняется в следующем порядке (см. `config/middleware.php`):

```
请求 → Cors → Locale(Accept-Language) → SecurityMiddleware (erikwang2013/security-php, 31种检测器) → RateLimit → [路由组中间件: AdminAuth → AdminPermission → OperationLog] → Controller
```

| Уровень | Промежуточное ПО/механизм | Цель защиты |
|----|--------|---------|
| 1 | SecurityMiddleware (erikwang2013/security-php) | 31 детектор атак + проверка HTTP-методов + ограничение размера тела + проверка Content-Type + CSRF + эскалация IP в чёрный список |
| 2 | Cors | Безопасность кросс-доменных запросов + инъекция защитных заголовков ответа |
| 3 | RateLimit | Redis-лимит со скользящим окном, защита от brute force |
| 4 | AdminAuth | Аутентификация JWT + выход через чёрный список |
| 5 | AdminPermission | Авторизация RBAC с точностью method.path |
| 6 | OperationLog | Аудит операций + трассировка источника |
| 7 | Шифрование данных | Обфускация ID Hashids + шифрование БД Encryptable + транспортное шифрование EncryptionService |

Фронтенд (Flutter) имеет собственные независимые проверки ввода на трёх уровнях; бэкенд не доверяет данным, каждый уровень защищается независимо.

## 2. Движок обнаружения атак

## 2. Движок обнаружения атак (erikwang2013/security-php)

Обнаружение атак мигрировало с самодельного SecurityMiddleware (erikwang2013/security-php) на специализированный пакет безопасности `erikwang2013/security-php` v1.1+, предоставляющий **31 детектор**, покрывающий 5 крупных категорий атак.

### 2.1 Классификация детекторов

**Инъекционные атаки (11 видов):** XSS, SQL-инъекции, инъекции команд, NoSQL-инъекции, LDAP-инъекции, XPath-инъекции, JNDI/Log4Shell, SSI (server-side includes), GraphQL-инъекции, SSTI (шаблонные инъекции)

**Протокольные и запросные атаки (9 видов):** SSRF, XXE, инъекции в HTTP-заголовки ответа, атаки на Host-заголовок, Request Smuggling, Open Redirect, обход CORS, угон WebSocket, DNS Rebinding

**Проверки уровня HTTP-протокола (6 видов):** проверка HTTP-методов (405), ограничение размера тела запроса (413), проверка Content-Type (415), CSRF-проверка Origin, эскалация IP в чёрный список, обнаружение утечки чувствительных данных

**Атаки на данные и сериализацию (5 видов):** PHP-десериализация, инъекции CSV-формул, инъекции в почтовые заголовки, JWT-атаки (структурный анализ), JS Prototype Pollution

**Файловые и путевые атаки (2 вида):** обход путей, загрузка вредоносных файлов

### 2.2 Режимы обработки

Каждый детектор независимо поддерживает два режима:
- `block` — при обнаружении атаки блокирует запрос и возвращает настроенный код состояния
- `log` — только записывает в журнал без блокировки (`header_injection`, `ssti`, `nosql_injection` по умолчанию в режиме log для защиты от ложных срабатываний)

### 2.3 Эскалация IP в чёрный список

5 срабатываний детекторов атак с одного IP за 60 секунд → автоматическая блокировка на 15 минут. Бэкенд хранения выбирается: Redis (распределённый), File (JSON на одном узле) или Cache (отдельный файл при высокой нагрузке); в текущей конфигурации — Redis.

### 2.4 Журнал безопасности

Расположение файла: `runtime/logs/security.log` (автоматическая ротация, 10MB/файл)

## 4. Защитные заголовки ответа

Все заголовки инъектируются в middleware `Cors` через `$response->withHeaders()` и добавляются к каждому ответу.

| Заголовок | Значение | Назначение |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | Разрешены кросс-доменные запросы с любых источников (сценарий внутренней админ-панели) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | Разрешённые методы |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | Разрешённые пользовательские заголовки |
| Access-Control-Max-Age | `86400` | Кэширование preflight-запроса 24 часа |
| X-Content-Type-Options | `nosniff` | Запрет MIME-сниффинга в браузере |
| X-Frame-Options | `DENY` | Запрет встраивания в любые iframe, защита от clickjacking |
| X-XSS-Protection | `1; mode=block` | Включение встроенного XSS-фильтра браузера с блокировкой рендеринга страницы |
| Referrer-Policy | `strict-origin-when-cross-origin` | При одном источнике — полный URL, кросс-домен — только домен |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | Глобальный запрет API камеры/микрофона/геолокации |

Preflight-запрос OPTIONS напрямую возвращает пустой ответ 204 без входа в последующую цепочку промежуточного ПО.

### 4.2 Content-Security-Policy (CSP)

Наряду с другими защитными заголовками инъектируется в middleware Cors для эшелонированной обороны: ограничивает источники ресурсов, которые браузер может загружать и исполнять.

| Заголовок | Значение | Назначение |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | Ограничение источников скриптов/стилей/изображений/соединений/фреймов/форм |
| X-Permitted-Cross-Domain-Policies | `none` | Запрет загрузки кросс-доменных policy-файлов Adobe Flash/PDF |

Ключевые положения CSP:
- `default-src 'self'`: по умолчанию разрешены только ресурсы того же источника
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: разрешены скрипты того же источника + инлайн-скрипты (необходимо для Flutter Web) + eval (необходимо для отладки Flutter Web)
- `frame-ancestors 'none'`: запрет встраивания в iframe любой страницей — двойная страховка с X-Frame-Options: DENY
- `base-uri 'self'`: тег `<base>` может указывать только на тот же источник
- `form-action 'self'`: формы могут отправляться только на тот же источник

## 5. Политика лимитов запросов

### Алгоритм

Скользящее окно Redis Sorted Set + атомарный Lua-скрипт, ключевые операции:

```lua
-- 1. 清理窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. 检查当前窗口计数
local count = redis.call('ZCARD', KEYS[1])
-- 3. 超限则返回 {0, count}，未超限则 ZADD 并返回 {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- 随机后缀避免同毫秒覆盖
redis.call('EXPIRE', KEYS[1], window + 10)
```

Lua-скрипт исполняется на сервере Redis в одном потоке — **естественная атомарность** устраняет гонку TOCTOU (Time-of-check to Time-of-use).

### Конфигурация лимитов

| Маршрут | Лимит | Окно | Сценарий |
|------|------|------|------|
| По умолчанию (все маршруты) | 60 раз/мин | 60s | Обычные API |
| `/api/auth/login` | 10 раз/мин | 60s | Вход (защита от brute force) |
| `/api/auth/register` | 5 раз/мин | 60s | Регистрация (защита от массовой регистрации) |

### Заголовки ответа

При срабатывании лимита возвращаются HTTP 429 и JSON body:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

Все ответы (включая нормальные) несут следующие заголовки:

| Заголовок | Описание |
|----|------|
| X-RateLimit-Limit | Максимальное число запросов в текущем окне |
| X-RateLimit-Remaining | Оставшееся число запросов в текущем окне |
| X-RateLimit-Reset | Unix-временная метка сброса окна |
| Retry-After | Присутствует только при срабатывании лимита; рекомендуемое число секунд ожидания |

### Стратегия деградации

При сбое Redis (таймаут соединения, недоступность и т. п.) — **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis down, 放行所有请求
}
```

Лучше кратковременно потерять защиту лимитов, чем блокировать нормальные бизнес-запросы.

### 5.4 Механизм блокировки учётной записи

Помимо ограничения частоты, эндпоинт входа дополнительно использует **блокировку учётной записи** для защиты от направленного brute force по конкретному пользователю.

**Процесс блокировки**:

```
登录失败 → Redis INCR account_lockout:{userId} TTL=900s
连续 5 次失败 → Redis SETEX account_locked:{userId} 900 1
            → 返回 429 "账号已被锁定，请15分钟后再试"
            → 清除计数器 DEL account_lockout:{userId}
```

**Поведение в период блокировки**:

В период блокировки все запросы входа сразу возвращают 429 без проверки пароля — попытки brute force полностью блокируются.

**Константы конфигурации**:

| Константа | Значение | Смысл |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | Максимальное число неудачных попыток подряд |
| LOCKOUT_DURATION | 900 | Длительность блокировки (сек), т. е. 15 минут |

Примечание: блокировка привязана к `userId`, а не к IP, поэтому смена IP не обходит блокировку. В сочетании с IP-лимитом (10 раз/мин) формируется двойная защита:
- На уровне IP: лимит 10 раз/мин блокирует распределённый brute force
- На уровне учётной записи: блокировка после 5 неудач блокирует направленный brute force

## 6. Аутентификация и авторизация

### 6.1 Аутентификация JWT

Реализована middleware AdminAuth, подключённым к группам маршрутов, требующим аутентификации.

**Параметры конфигурации** (`config/plugin/erikwang2013/jwt/jwt`, инъекция из `.env`):

| Параметр | Значение | Описание |
|------|-----|------|
| Алгоритм | HS256 | Симметричная подпись HMAC-SHA256 |
| Ключ | `JWT_SECRET` | Инъекция из переменной окружения; в продакшене обязательна замена |
| TTL access_token | 7200s (2h) | `JWT_TTL` |
| TTL refresh_token | 1209600s (14d) | `JWT_REFRESH_TTL` |
| Эмитент | `open-admin` | `JWT_ISSUER` |
| Аудитория | `open-admin` | `JWT_AUDIENCE` |

**Извлечение Token**: из заголовка `Authorization: Bearer <token>`, срезается префикс `Bearer ` — получается исходный JWT.

**Процесс аутентификации**:
1. Пустой token → сразу 401 `{"code": 401, "message": "未登录"}`
2. Проверка чёрного списка Redis `jwt_blacklist:{md5(token)}` → совпадение → 401 `Token已失效，请重新登录`
3. JWT decode → неудача (истёк/несовпадение подписи) → 401 `Token已过期或无效`
4. Успех → инъекция `$request->adminId` и `$request->adminUsername`

**Механизм чёрного списка**: при выходе пользователя `md5(token)` записывается в Redis с TTL, равным оставшемуся сроку действия JWT. При сбое Redis проверка чёрного списка пропускается (fail-open); в этом случае вышедший токен может кратко использоваться, но короткий срок самого JWT (2h) служит резервной защитой.

### 6.2 Ограничение одновременных сессий

Чтобы токен после утечки не использовался массово на нескольких устройствах, система ограничивает число одновременно действующих Token одного пользователя.

**Логика ограничения**:

```
登录成功 → 签发新 Token
         → 查询当前用户有效 Token 数量: Redis SCARD user_tokens:{userId}
         → 若数量 >= 3（MAX_CONCURRENT_SESSIONS）:
            → 按创建时间升序排列，移除最旧的 Token:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → 将新 Token 加入集合: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**Константы конфигурации**:

| Константа | Значение | Смысл |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | Максимальное число одновременных Token одного пользователя |

**Сценарий вытеснения**: когда пользователь входит с 4-го устройства, Token 1-го устройства принудительно добавляется в чёрный список, последующие запросы возвращают 401 "Token已失效，请重新登录".

При выходе текущий Token удаляется из множества. При естественном истечении Token ключ Redis автоматически удаляется, и число членов множества уменьшается.

### 6.3 Модель прав RBAC

Реализована middleware AdminPermission.

**Модель данных**: трёхуровневая связь User -> Role -> Permission

- `erik_admin_user` (таблица пользователей)
- `erik_admin_user_role` (таблица связей пользователь-роль)
- `erik_admin_role` (таблица ролей)
- `erik_admin_role_permission` (таблица связей роль-право)
- `erik_admin_permission` (таблица прав)

**Типы прав**:
| type | Значение | Пример |
|------|------|------|
| 1 | Право меню | Управление видимостью левой навигации |
| 2 | Право кнопки | Управление кнопками действий на странице (создание/редактирование/удаление) |
| 3 | Право API | Управление вызовами бэкенд-интерфейсов |

Формат идентификатора API-права: `{method}.{path}`

Например:
- `post.admin/user` — создание пользователя
- `put.admin/user` — редактирование пользователя
- `delete.admin/user` — удаление пользователя
- `get.admin/user` — просмотр списка пользователей

**Процесс авторизации**:
1. `$request->adminId` пуст → пропуск (маршрут не требует предварительной аутентификации)
2. Получение пользователя → роли (пропуск отключённых ролей со `status=0`) → список прав
3. Супер-администратор (`slug = '*'`) → прямой пропуск
4. Формирование `strtolower(method) . '.' . trim(path, '/')` → сравнение со списком прав
5. Нет совпадения → 403 `{"code": 403, "message": "无权限访问"}`

**Повторное подтверждение**: BaseController предоставляет метод `confirmPassword()`; чувствительные операции (удаление пользователей, экспорт данных и т. п.) на уровне контроллера дополнительно требуют ввода текущего пароля, чтобы предотвратить неавторизованные действия после угона сессии.

## 7. Журналы аудита

### 7.1 Журнал операций

Middleware OperationLog автоматически записывает журнал операций для запросов POST / PUT / DELETE. GET-запросы не записываются.

**Записываемые поля**:

| Поле | Источник | Описание |
|------|------|------|
| id | SnowflakeService::generate() | Глобально уникальный ID |
| user_id | `$request->adminId` | ID оператора; 0, если не авторизован |
| action | `$request->method()` | Равен method |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | Путь запроса |
| ip | `$request->getRealIp()` | Реальный IP клиента |
| source | detectSource() | Платформа источника клиента |
| input | тело запроса (JSON после маскирования) | Отправленные данные операции |
| created_at | `date('Y-m-d H:i:s')` | Время операции |

**Фильтрация чувствительных полей**: при рекурсивном обходе тела запроса значения следующих полей заменяются на `***`:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**Определение источника** (`detectSource()`), по приоритету:

1. Сначала читается пользовательский заголовок `X-Client-Platform` (явное указание нативного клиента)
2. Иначе — вывод по строке User-Agent (порядок проверок в методе `detectSource()`):

| Платформа | Ключевые слова UA |
|------|----------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | запасное значение по умолчанию |

**Отказоустойчивость**: ошибка записи журнала не блокирует бизнес-запрос (исключение `catch (\Throwable)` молча поглощается).

### 7.2 Журнал безопасности

**Расположение файла**: `runtime/logs/security.log`

**Записываемое содержимое**:
- Журнал блокировки атак: категория атаки, IP, путь, поле, источник, фрагмент payload (первые 200 символов)
- Уведомления о блокировке IP: заблокированный IP, число срабатываний

Права записи журнала — `FILE_APPEND | LOCK_EX`, гарантирующие безопасность конкурентной записи.

## 8. Защита данных

Система использует трёхуровневую стратегию защиты данных, соответствующую трём этапам движения данных.

### 8.1 Транспортный уровень — EncryptionService

`EncryptionService` использует пакет `erikwang2013/encryption` для шифрования/расшифровки чувствительных полей в запросах/ответах API.

**Технические детали**:
- Алгоритм: `aes-256-cbc-hmac` (встроенная подпись HMAC против подмены)
- Ключ: переменная окружения `ENCRYPTION_KEY`, автоматически выравнивается до 32 байт
- Применение: передача телефона, номера удостоверения и других полей между клиентом и API

**Утилиты маскирования**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (имя пользователя длиннее 2 символов) или `a**@example.com`

### 8.2 Уровень хранения — Encryptable Cast

Модель `AdminUser` использует Eloquent cast `Erikwang2013\Encryptable\Encryptable` для полей:

- `email` → cast Encryptable, автоматическое шифрование/расшифровка
- `phone` → cast Encryptable, автоматическое шифрование/расшифровка  
- `id_card` → cast Encryptable, автоматическое шифрование/расшифровка

При записи в БД поле автоматически шифруется в шифротекст, при чтении автоматически расшифровывается. Тип колонки в БД — `VARCHAR(500)`, шифротекст хранится в base64.

**Ключевая система**: используется отдельный от транспортного шифрования (`ENCRYPTION_KEY`) ключ `ENCRYPTABLE_KEY`; утечка одного ключа не выводит из строя другой уровень.

Ротация ключей: переменная окружения `ENCRYPTION_PREVIOUS_KEYS` поддерживает список исторических ключей (через запятую); при чтении старых данных пробуются исторические ключи, при записи данные шифруются текущим ключом.

### 8.3 Уровень отображения — обфускация ID и маскирование

**Обфускация ID Hashids**: `HashidsService` использует пакет `erikwang2013/hashids`.

- Исходные BIGINT ID из внешних ответов API кодируются в hash-строки (например `xK3mN9qR2pL7wV8b`)
- Клиент передаёт hash-строку, бэкенд автоматически декодирует её в исходный ID
- Соль `HASHIDS_SALT` инъектируется из переменной окружения; разные соли дают полностью разные результаты кодирования
- Минимальная длина hash — 16 символов, используется 62-символьный буквенно-цифровой алфавит
- BaseController предоставляет удобные методы `encodeId()`, `decodeId()`, `encodeIds()`

**Маскирование при экспорте**: при экспорте Excel/PDF (ExportController) чувствительные поля единообразно маскируются:
- Телефон: `138****1234`
- Email: `a***@example.com`
- Удостоверение личности: полностью скрывается как `********`

## 9. Управление ключами

Все ключи инъектируются через переменные окружения `.env`; конфигурационные файлы читают их через `getenv()` со встроенными значениями по умолчанию (безопасны только для разработки).

| Переменная окружения | Назначение | Пакет | Требование для продакшена |
|----------|------|-----|---------|
| JWT_SECRET | Секрет подписи JWT | erikwang2013/jwt-webman | Случайная строка из 64+ символов |
| JWT_ALGORITHM | Алгоритм подписи JWT | тот же | Оставить HS256 |
| HASHIDS_SALT | Соль кодирования ID | erikwang2013/hashids | Случайная строка |
| SNOWFLAKE_DATACENTER_ID | ID дата-центра (0-31) | erikwang2013/snowflake-php | Для одного ЦОД оставить по умолчанию |
| ENCRYPTION_KEY | Ключ транспортного шифрования API | erikwang2013/encryption | Случайная строка 32 байта |
| ENCRYPTABLE_KEY | Ключ шифрования уровня БД | erikwang2013/encryptable | Случайная строка 32 байта, отличная от транспортного ключа |

**Требования безопасности**:
- Файл `.env` добавлен в `.gitignore`; строго запрещено коммитить его в репозиторий
- `.env.example` — публичный шаблон без реальных ключей
- В продакшене **обязательно** заменить все ключи по умолчанию на случайные строки
- Рекомендуется генерировать ключи через `openssl rand -base64 32`

### Изоляция хранения ключей

| Уровень | Ключ конфигурации | Переменная окружения ключа |
|----|--------|-------------|
| Транспортное шифрование | `config/encryption.php` → `key` | `ENCRYPTION_KEY` |
| Шифрование хранения | `config/encryptable.php` → `key` | `ENCRYPTABLE_KEY` |
| Обфускация ID | `config/hashids.php` → `connections.main.salt` | `HASHIDS_SALT` |
| Подпись JWT | `config/plugin/erikwang2013/jwt/jwt` | `JWT_SECRET` |

## 10. security.txt (RFC 9116)

Система предоставляет эндпоинт контактных данных безопасности `/.well-known/security.txt` по стандарту RFC 9116, чтобы исследователи безопасности могли быстро найти канал для сообщения об уязвимостях.

**Способ доступа**:

```
GET /.well-known/security.txt
```

**Содержимое ответа**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**Описание полей**:

| Поле | Описание |
|------|------|
| Contact | Контакт для сообщения об уязвимостях безопасности |
| Expires | Срок действия файла, требуется периодическое обновление |
| Preferred-Languages | Предпочитаемые языки общения |
| Canonical | Канонический URL этого файла |
| Policy | Ссылка на политику безопасности / политику раскрытия уязвимостей |

Этот эндпоинт не ограничен лимитами, аутентификацией и другим промежуточным ПО — доступен всем напрямую.

## 11. Безопасная конфигурация Nginx

Проект предоставляет `docs/nginx-security.conf` как справочную конфигурацию усиления безопасности обратного прокси Nginx для продакшена.

**Включённые меры безопасности**:

| Параметр конфигурации | Назначение |
|--------|------|
| `server_tokens off` | Скрытие номера версии Nginx |
| `client_max_body_size 10m` | Ограничение размера тела запроса, совместно с SecurityMiddleware (erikwang2013/security-php) |
| `limit_req_zone` | Ограничение частоты запросов на уровне Nginx |
| `limit_conn_zone` | Ограничение числа одновременных соединений |
| `add_header` защитные заголовки | Добавление на уровне Nginx защитных заголовков, таких как X-XSS-Protection |
| `if ($request_method)` | Отказ на уровне Nginx нестандартным HTTP-методам |
| SSL/TLS конфигурация | Современная конфигурация TLS 1.2/1.3, отключение слабых шифр-наборов |
| Скрытие бэкенд-заголовков | `proxy_hide_header` удаляет чувствительные заголовки, такие как версия webman |

**Способ использования**: объедините конфигурацию из `docs/nginx-security.conf` с вашим блоком server в Nginx, скорректировав домен и пути к сертификатам.

## 12. Модель угроз

### 12.1 Защищённые угрозы

| Тип угрозы | Вектор атаки | Уровни защиты |
|----------|---------|---------|
| Злоупотребление HTTP-методами | TRACE/TRACK XST-атаки, CONNECT-туннелирование через прокси, перебор методов WebDAV | Детектор http_method в SecurityMiddleware, белый список методов, 405 |
| Направленный brute force | Многократный подбор пароля конкретного пользователя | Блокировка учётной записи (5 неудач — блокировка 15 мин) + RateLimit (вход 10/мин) + Captcha |
| Brute force | Перебор имён пользователей/паролей с распределённых IP | RateLimit (вход 10/мин) + Captcha |
| XSS (межсайтовый скриптинг) | `<script>`, onerror, javascript: | SecurityMiddleware (erikwang2013/security-php) (5 режимов) + заголовок X-XSS-Protection + CSP |
| SQL-инъекции | UNION SELECT, OR 1=1, обход комментариями | SecurityMiddleware (erikwang2013/security-php) (6 режимов) + параметризованные запросы Eloquent ORM |
| CSRF (подделка межсайтовых запросов) | Вредоносный сайт отправляет запросы от имени пользователя | Проверка Origin/Referer в SecurityMiddleware (erikwang2013/security-php) |
| Обход путей | `../../etc/passwd` | Режим обхода путей в SecurityMiddleware (erikwang2013/security-php) + белый список расширений в UploadController |
| Инъекции команд | `;ls`, `` `whoami` ``, `$(cat ...)` | SecurityMiddleware (erikwang2013/security-php) (4 режима) |
| Угон сессии | Кража JWT Token | Короткий срок JWT (2h) + выход через чёрный список + повторное подтверждение паролем чувствительных операций |
| Перебор ID | Перебор числовых ID для оценки объёма данных | Обфускация Hashids в случайные строки |
| Утечка данных | Выгрузка БД / man-in-the-middle / утечка журналов | Трёхуровневое шифрование/маскирование + фильтрация чувствительных полей в OperationLog |
| DoS-атаки | Чрезмерно большие тела запросов / высокая частота | Ограничение тела 10MB + RateLimit 60/мин + чёрный список IP |
| Повышение привилегий | Доступ низкопривилегированного пользователя к интерфейсам админки | Авторизация RBAC с точностью method.path |
| Атаки через загрузку файлов | Двойное расширение shell.php.png | Детектор вредоносных файлов в SecurityMiddleware (erikwang2013/security-php) |

### 12.2 Известные ограничения

| Ограничение | Сфера влияния | Меры смягчения |
|------|---------|---------|
| CSRF-защита действует только для браузера | Небраузерные клиенты (curl, Postman, мобильные приложения) обходят проверку Origin/Referer | Небраузерные клиенты от природы не подвержены CSRF; вместо Cookie используется аутентификация JWT |
| При недоступности Redis лимиты и чёрный список деградируют в fail-open | Атакующий может обойти лимиты и высокочастотную блокировку | Мониторинг доступности Redis с алертами; чёрный список IP поддерживает три бэкенда file/redis/cache с деградацией |
| Нет отдельного WAF-движка | Обнаружение на основе регулярных выражений, не специализированный WAF | В продакшене рекомендуется Nginx ModSecurity или Cloudflare WAF перед приложением |
| JWT без состояния нельзя принудительно аннулировать | До истечения срока токен нельзя отозвать на сервере (кроме чёрного списка) | Чёрный список + короткий TTL 2h снижают окно риска |
| Нет особых лимитов для эндпоинтов администратора | Интерфейсы админки делят общий лимит 60/мин с обычными | Частота действий администратора от природы низкая, пока нет необходимости разделять |
| Ограничение возврата в PCRE | В пакете предел возврата 1 000 000 + восстановление в finally; сверхсложные входные данные всё же несут риск по производительности | Запасная мера — ограничение размера тела (10MB) |
