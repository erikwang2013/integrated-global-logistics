## 1. गहन सुरक्षा पैनोरमा

सिस्टम 7-परत गहन सुरक्षा मॉडल अपनाता है, बाहर से अंदर तक परत-दर-परत दुर्भावनापूर्ण रिक्वेस्ट को फ़िल्टर करता है, यह सुनिश्चित करता है कि किसी भी एक परत के विफल होने पर भी आगे की रक्षा रेखाएँ मौजूद रहें।

पूरी मिडलवेयर चेन निम्न क्रम में निष्पादित होती है (`config/middleware.php` देखें):

```
रिक्वेस्ट → Cors → Locale(Accept-Language) → SecurityMiddleware (erikwang2013/security-php, 31 डिटेक्टर) → RateLimit → [रूट ग्रुप मिडलवेयर: AdminAuth → AdminPermission → OperationLog] → Controller
```

| परत | मिडलवेयर/तंत्र | सुरक्षा लक्ष्य |
|----|--------|---------|
| 1 | SecurityMiddleware (erikwang2013/security-php) | 31 प्रकार की अटैक डिटेक्शन + HTTP मेथड सत्यापन + रिक्वेस्ट बॉडी आकार सीमा + Content-Type सत्यापन + CSRF + IP अटैक एस्केलेशन ब्लैकलिस्ट |
| 2 | Cors | क्रॉस-ओरिजिन सुरक्षा + रिस्पॉन्स सुरक्षा हेडर इंजेक्शन |
| 3 | RateLimit | Redis स्लाइडिंग विंडो रेट लिमिट, ब्रूट-फोर्स रोकथाम |
| 4 | AdminAuth | JWT प्रमाणीकरण + ब्लैकलिस्ट लॉगआउट |
| 5 | AdminPermission | RBAC method.path ग्रैन्युलरिटी प्रमाणीकरण |
| 6 | OperationLog | ऑपरेशन ऑडिट + स्रोत डिवाइस ट्रेसिंग |
| 7 | डेटा एन्क्रिप्शन | Hashids ID ऑबफ़स्केशन + Encryptable DB एन्क्रिप्शन + EncryptionService ट्रांसमिशन एन्क्रिप्शन |

फ्रंटएंड तीन परतों (Flutter) में अलग स्वतंत्र इनपुट सत्यापन होता है; बैकएंड किसी पर भरोसा नहीं करता, हर परत स्वतंत्र रूप से रक्षा करती है।

## 2. अटैक डिटेक्शन इंजन

## 2. अटैक डिटेक्शन इंजन (erikwang2013/security-php)

अटैक डिटेक्शन को सेल्फ-डेवलप्ड SecurityMiddleware (erikwang2013/security-php) से `erikwang2013/security-php` v1.1+ समर्पित सुरक्षा पैकेज में माइग्रेट किया गया है, जो **31 प्रकार के डिटेक्टर** प्रदान करता है, 5 बड़ी अटैक श्रेणियों को कवर करता है।

### 2.1 डिटेक्टर वर्गीकरण

**इंजेक्शन अटैक (11 प्रकार):** XSS、SQL इंजेक्शन、कमांड इंजेक्शन、NoSQL इंजेक्शन、LDAP इंजेक्शन、XPath इंजेक्शन、JNDI/Log4Shell、SSI सर्वर-साइड इनक्लूड、GraphQL इंजेक्शन、SSTI टेम्पलेट इंजेक्शन

**प्रोटोकॉल और रिक्वेस्ट अटैक (9 प्रकार):** SSRF、XXE、HTTP रिस्पॉन्स हेडर इंजेक्शन、Host हेडर अटैक、Request Smuggling、Open Redirect、CORS बाईपास、WebSocket हाईजैकिंग、DNS Rebinding

**HTTP प्रोटोकॉल परत सत्यापन (6 प्रकार):** HTTP मेथड सत्यापन(405)、रिक्वेस्ट बॉडी आकार सीमा(413)、Content-Type सत्यापन(415)、CSRF Origin जाँच、IP अटैक एस्केलेशन ब्लैकलिस्ट、संवेदनशील डेटा लीक डिटेक्शन

**डेटा और सीरियलाइज़ेशन अटैक (5 प्रकार):** PHP डीसीरियलाइज़ेशन、CSV फॉर्मूला इंजेक्शन、ईमेल हेडर इंजेक्शन、JWT अटैक（संरचनात्मक विश्लेषण）、JS Prototype Pollution

**फ़ाइल और पाथ अटैक (2 प्रकार):** पाथ ट्रैवर्सल、दुर्भावनापूर्ण फ़ाइल अपलोड

### 2.2 हैंडलिंग मोड

हर डिटेक्टर स्वतंत्र रूप से दो मोड समर्थित करता है:
- `block` — अटैक पहचानते ही इंटरसेप्ट करें, कॉन्फ़िगर किया गया स्टेटस कोड लौटाएँ
- `log` — केवल लॉग रिकॉर्ड करें, इंटरसेप्ट नहीं करें (`header_injection`、`ssti`、`nosql_injection` डिफ़ॉल्ट रूप से log मोड, गलत अलार्म रोकथाम)

### 2.3 IP अटैक एस्केलेशन ब्लैकलिस्ट

एक ही IP 60 सेकंड में 5 बार अटैक डिटेक्शन ट्रिगर करता है → स्वचालित रूप से 15 मिनट के लिए बैन। स्टोरेज बैकएंड वैकल्पिक: Redis (वितरित)、File (सिंगल-मशीन JSON) या Cache (उच्च समवर्ती स्वतंत्र फ़ाइल); वर्तमान कॉन्फ़िगरेशन Redis स्टोरेज है।

### 2.4 सुरक्षा लॉग

फ़ाइल स्थान: `runtime/logs/security.log` (स्वचालित रोटेशन, 10MB/फ़ाइल)

## 4. रिस्पॉन्स सुरक्षा हेडर

सभी हेडर `Cors` मिडलवेयर में इंजेक्ट होते हैं, `$response->withHeaders()` के माध्यम से हर रिस्पॉन्स में जुड़ते हैं।

| हेडर | मान | कार्य |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | किसी भी ओरिजिन को क्रॉस-ओरिजिन की अनुमति (इंट्रानेट एडमिन पैनल परिदृश्य) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | अनुमत मेथड सेट |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | अनुमत कस्टम हेडर |
| Access-Control-Max-Age | `86400` | प्रीफ्लाइट रिक्वेस्ट कैश 24 घंटे |
| X-Content-Type-Options | `nosniff` | ब्राउज़र MIME स्निफिंग प्रतिबंधित |
| X-Frame-Options | `DENY` | सभी iframe एम्बेडिंग प्रतिबंधित, क्लिकजैकिंग रोकथाम |
| X-XSS-Protection | `1; mode=block` | ब्राउज़र अंतर्निहित XSS फ़िल्टर सक्षम और पेज रेंडरिंग इंटरसेप्ट |
| Referrer-Policy | `strict-origin-when-cross-origin` | समान ओरिजिन पर पूर्ण URL, क्रॉस-ओरिजिन पर केवल डोमेन |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | पूरी साइट पर कैमरा/माइक्रोफ़ोन/लोकेशन API अक्षम |

OPTIONS प्रीफ्लाइट रिक्वेस्ट सीधे 204 खाली रिस्पॉन्स लौटाती है, आगे की मिडलवेयर चेन में प्रवेश नहीं करती।

### 4.2 Content-Security-Policy (CSP)

अन्य सुरक्षा हेडर के साथ Cors मिडलवेयर में इंजेक्ट होता है, गहन सुरक्षा प्रदान करता है, ब्राउज़र द्वारा लोड और निष्पादित किए जा सकने वाले संसाधन स्रोतों को सीमित करता है।

| हेडर | मान | कार्य |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | स्क्रिप्ट/स्टाइल/इमेज/कनेक्शन/फ्रेम/फॉर्म आदि संसाधन स्रोत सीमित |
| X-Permitted-Cross-Domain-Policies | `none` | Adobe Flash/PDF आदि क्रॉस-डोमेन पॉलिसी फ़ाइल लोडिंग प्रतिबंधित |

CSP नीति मुख्य बिंदु:
- `default-src 'self'`: डिफ़ॉल्ट रूप से केवल समान-ओरिजिन संसाधन
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: समान-ओरिजिन स्क्रिप्ट + इनलाइन स्क्रिप्ट (Flutter Web के लिए आवश्यक) + eval (Flutter Web डिबगिंग के लिए आवश्यक)
- `frame-ancestors 'none'`: किसी भी पेज में iframe एम्बेडिंग प्रतिबंधित, X-Frame-Options: DENY के साथ दोहरी सुरक्षा
- `base-uri 'self'`: `<base>` टैग केवल समान-ओरिजिन पर इंगित कर सकता है
- `form-action 'self'`: फॉर्म केवल समान-ओरिजिन पर सबमिट हो सकता है

## 5. रेट लिमिट नीति

### एल्गोरिदम

Redis Sorted Set स्लाइडिंग विंडो + Lua एटॉमिक स्क्रिप्ट, प्रमुख ऑपरेशन:

```lua
-- 1. विंडो के बाहर की पुरानी रिकॉर्ड साफ़ करें
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. वर्तमान विंडो काउंट जाँचें
local count = redis.call('ZCARD', KEYS[1])
-- 3. सीमा से अधिक होने पर {0, count} लौटाएँ, अन्यथा ZADD करके {1, count+1} लौटाएँ
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- रैंडम सफ़िक्स: एक ही मिलीसेकंड में ओवरराइट रोकें
redis.call('EXPIRE', KEYS[1], window + 10)
```

Lua स्क्रिप्ट Redis सर्वर साइड पर सिंगल-थ्रेडेड निष्पादित होती है, **स्वाभाविक रूप से एटॉमिक**, TOCTOU（Time-of-check to Time-of-use）रेस कंडीशन समाप्त।

### रेट लिमिट कॉन्फ़िगरेशन

| रूट | सीमा | विंडो | परिदृश्य |
|------|------|------|------|
| डिफ़ॉल्ट (सभी रूट) | 60 बार/मिनट | 60s | सामान्य API |
| `/api/auth/login` | 10 बार/मिनट | 60s | लॉगिन (ब्रूट-फोर्स रोकथाम) |
| `/api/auth/register` | 5 बार/मिनट | 60s | रजिस्ट्रेशन (बल्क रजिस्ट्रेशन रोकथाम) |

### रिस्पॉन्स हेडर

रेट लिमिट ट्रिगर होने पर HTTP 429 और JSON बॉडी लौटता है:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

सभी रिस्पॉन्स (सामान्य रिस्पॉन्स सहित) निम्न हेडर लेकर आते हैं:

| हेडर | विवरण |
|----|------|
| X-RateLimit-Limit | वर्तमान विंडो में अधिकतम अनुमत रिक्वेस्ट संख्या |
| X-RateLimit-Remaining | वर्तमान विंडो में शेष उपलब्ध रिक्वेस्ट संख्या |
| X-RateLimit-Reset | विंडो रीसेट का Unix टाइमस्टैम्प |
| Retry-After | केवल रेट लिमिट होने पर, प्रतीक्षा सेकंड सुझाव |

### डिग्रेडेशन नीति

Redis असामान्य (कनेक्शन टाइमआउट, अनुपलब्ध आदि) होने पर **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis down, सभी रिक्वेस्ट अनुमति
}
```

थोड़े समय के लिए रेट लिमिट सुरक्षा खोना बेहतर है, न कि सामान्य बिज़नेस रिक्वेस्ट को रोकना।

### 5.4 खाता लॉक तंत्र

लॉगिन इंटरफ़ेस रेट लिमिट के अतिरिक्त **खाता लॉक** तंत्र भी जोड़ता है, जो विशिष्ट उपयोगकर्ता को लक्षित ब्रूट-फोर्स से बचाता है।

**लॉक प्रवाह**:

```
लॉगिन विफल → Redis INCR account_lockout:{userId} TTL=900s
लगातार 5 बार विफल → Redis SETEX account_locked:{userId} 900 1
            → 429 "खाता लॉक हो चुका है, कृपया 15 मिनट बाद प्रयास करें"
            → काउंटर साफ़ करें DEL account_lockout:{userId}
```

**लॉक अवधि के दौरान व्यवहार**:

लॉक अवधि के दौरान सभी लॉगिन रिक्वेस्ट सीधे 429 लौटती हैं, पासवर्ड सत्यापन नहीं होता, ब्रूट-फोर्स प्रयास पूरी तरह रुक जाते हैं।

**कॉन्फ़िगरेशन कॉन्स्टेंट**:

| कॉन्स्टेंट | मान | अर्थ |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | अधिकतम लगातार विफलता संख्या |
| LOCKOUT_DURATION | 900 | लॉक अवधि (सेकंड), यानी 15 मिनट |

ध्यान दें: खाता लॉक `userId` पर आधारित है, IP पर नहीं, इसलिए हमलावर IP बदलकर लॉक को बाईपास नहीं कर सकते। IP रेट लिमिट (10 बार/मिनट) के साथ मिलकर दोहरी सुरक्षा बनती है:
- IP स्तर: 10 बार/मिनट रेट लिमिट वितरित ब्रूट-फोर्स रोकता है
- खाता स्तर: 5 बार विफल → लॉक, लक्षित ब्रूट-फोर्स रोकता है

## 6. प्रमाणीकरण और अनुमति

### 6.1 JWT प्रमाणीकरण

AdminAuth मिडलवेयर द्वारा लागू, प्रमाणीकरण आवश्यक रूट ग्रुप पर माउंट होता है।

**पैरामीटर कॉन्फ़िगरेशन** (`config/plugin/erikwang2013/jwt/jwt`，`.env` से इंजेक्ट):

| पैरामीटर | मान | विवरण |
|------|-----|------|
| एल्गोरिदम | HS256 | HMAC-SHA256 सममित सिग्नेचर |
| कुंजी | `JWT_SECRET` | पर्यावरण चर इंजेक्शन, प्रोडक्शन में बदलना आवश्यक |
| access_token TTL | 7200s (2h) | `JWT_TTL` |
| refresh_token TTL | 1209600s (14d) | `JWT_REFRESH_TTL` |
| जारीकर्ता | `open-admin` | `JWT_ISSUER` |
| ऑडियंस | `open-admin` | `JWT_AUDIENCE` |

**टोकन निष्कर्षण**: `Authorization: Bearer <token>` हेडर से निकाला जाता है, `Bearer ` प्रीफ़िक्स हटाकर मूल JWT मिलता है।

**प्रमाणीकरण प्रवाह**:
1. खाली टोकन → सीधे 401 `{"code": 401, "message": "未登录"}`
2. Redis ब्लैकलिस्ट `jwt_blacklist:{md5(token)}` जाँचें → हिट → 401 `Token已失效，请重新登录`
3. JWT decode → विफल (समाप्त/सिग्नेचर अमान्य) → 401 `Token已过期或无效`
4. सफल → `$request->adminId` और `$request->adminUsername` इंजेक्ट

**ब्लैकलिस्ट तंत्र**: उपयोगकर्ता लॉगआउट करते समय `md5(token)` Redis में लिखा जाता है, TTL JWT की शेष वैधता अवधि पर सेट होता है। Redis विफलता पर ब्लैकलिस्ट जाँच छोड़ दी जाती है (fail-open); इस स्थिति में लॉगआउट किया गया टोकन थोड़े समय के लिए उपयोग हो सकता है, लेकिन JWT की छोटी वैधता (2h) बैकअप सुरक्षा के रूप में काम करती है।

### 6.2 समवर्ती सत्र सीमा

टोकन लीक होने के बाद कई डिवाइसों पर दुरुपयोग रोकने के लिए, सिस्टम एक ही उपयोगकर्ता के पास एक साथ मौजूद मान्य टोकन की संख्या सीमित करता है।

**सीमा लॉजिक**:

```
लॉगिन सफल → नया टोकन जारी करें
         → वर्तमान उपयोगकर्ता के मान्य टोकन की संख्या जाँचें: Redis SCARD user_tokens:{userId}
         → यदि संख्या >= 3 (MAX_CONCURRENT_SESSIONS):
            → निर्माण समय के आरोही क्रम में, सबसे पुराना टोकन हटाएँ:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → नया टोकन सेट में जोड़ें: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**कॉन्फ़िगरेशन कॉन्स्टेंट**:

| कॉन्स्टेंट | मान | अर्थ |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | एक ही उपयोगकर्ता के अधिकतम समवर्ती टोकन |

**बलपूर्वक लॉगआउट परिदृश्य**: जब उपयोगकर्ता चौथे डिवाइस पर लॉगिन करता है, तो पहले डिवाइस का टोकन बलपूर्वक ब्लैकलिस्ट में जाता है, बाद की रिक्वेस्ट 401 "Token已失效，请重新登录" लौटाती है।

लॉगआउट करते समय वर्तमान टोकन सेट से हट जाता है। टोकन स्वाभाविक रूप से समाप्त होने पर Redis key स्वचालित रूप से अमान्य हो जाती है, सेट सदस्य उसी अनुपात में घटते हैं।

### 6.3 RBAC अनुमति मॉडल

AdminPermission मिडलवेयर द्वारा लागू।

**डेटा मॉडल**: User -> Role -> Permission तीन-परत संबंध

- `logistics_admin_user` (उपयोगकर्ता टेबल)
- `logistics_admin_user_role` (उपयोगकर्ता-भूमिका संबंध टेबल)
- `logistics_admin_role` (भूमिका टेबल)
- `logistics_admin_role_permission` (भूमिका-अनुमति संबंध टेबल)
- `logistics_admin_permission` (अनुमति टेबल)

**अनुमति प्रकार**:
| type | अर्थ | उदाहरण |
|------|------|------|
| 1 | मेनू अनुमति | बाईं नेविगेशन दृश्यता नियंत्रण |
| 2 | बटन अनुमति | पेज के भीतर ऑपरेशन बटन (नया/संपादित/हटाएँ) नियंत्रण |
| 3 | API अनुमति | बैकएंड इंटरफ़ेस कॉल नियंत्रण |

API अनुमति पहचानकर्ता फॉर्मेट: `{method}.{path}`

उदाहरण के लिए:
- `post.admin/user` — उपयोगकर्ता बनाना
- `put.admin/user` — उपयोगकर्ता संपादित करना
- `delete.admin/user` — उपयोगकर्ता हटाना
- `get.admin/user` — उपयोगकर्ता सूची देखना

**प्रमाणीकरण प्रवाह**:
1. `$request->adminId` खाली → अनुमति दें (रूट में प्रमाणीकरण प्रीसेट नहीं)
2. उपयोगकर्ता → भूमिकाएँ (status=0 वाली अक्षम भूमिकाएँ छोड़ें) → अनुमति सूची प्राप्त करें
3. सुपर एडमिन (`slug = '*'`) → सीधे अनुमति दें
4. `strtolower(method) . '.' . trim(path, '/')` निर्माण → अनुमति सूची से तुलना
5. मिलान विफल → 403 `{"code": 403, "message": "无权限访问"}`

**पुनः पुष्टि**: BaseController `confirmPassword()` मेथड प्रदान करता है; संवेदनशील ऑपरेशन (उपयोगकर्ता हटाना, डेटा निर्यात आदि) के लिए Controller परत में अतिरिक्त रूप से वर्तमान पासवर्ड इनपुट आवश्यक होता है, ताकि सत्र हाईजैक के बाद अनधिकृत ऑपरेशन को रोका जा सके।

## 7. ऑडिट लॉग

### 7.1 ऑपरेशन लॉग

OperationLog मिडलवेयर POST / PUT / DELETE रिक्वेस्ट पर ऑपरेशन लॉग स्वचालित रूप से रिकॉर्ड करता है। GET रिक्वेस्ट रिकॉर्ड नहीं होती।

**रिकॉर्ड फ़ील्ड**:

| फ़ील्ड | स्रोत | विवरण |
|------|------|------|
| id | SnowflakeService::generate() | वैश्विक अद्वितीय ID |
| user_id | `$request->adminId` | ऑपरेटर ID, लॉगिन न करने पर 0 |
| action | `$request->method()` | method के समान |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | रिक्वेस्ट पाथ |
| ip | `$request->getRealIp()` | क्लाइंट वास्तविक IP |
| source | detectSource() | क्लाइंट स्रोत प्लेटफ़ॉर्म |
| input | रिक्वेस्ट बॉडी (मास्क किया गया JSON) | ऑपरेशन सबमिट डेटा |
| created_at | `date('Y-m-d H:i:s')` | ऑपरेशन समय |

**संवेदनशील फ़ील्ड फ़िल्टर**: रिक्वेस्ट बॉडी को रिकर्सिवली ट्रैवर्स करता है, निम्न फ़ील्ड के मान `***` से बदल दिए जाते हैं:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**स्रोत डिवाइस पहचान** (`detectSource()`): प्राथमिकता क्रम:

1. पहले `X-Client-Platform` कस्टम हेडर पढ़ें (नेटिव क्लाइंट स्पष्ट घोषणा)
2. अन्यथा User-Agent स्ट्रिंग से अनुमान (`detectSource()` मेथड पहचान क्रम):

| प्लेटफ़ॉर्म | UA कीवर्ड |
|------|----------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | फॉलबैक डिफ़ॉल्ट मान |

**फॉल्ट टॉलरेंस**: लॉग लिखने में असामान्यता बिज़नेस रिक्वेस्ट को ब्लॉक नहीं करती (`catch (\Throwable)` मौन रूप से दबा दिया जाता है)।

### 7.2 सुरक्षा लॉग

**फ़ाइल स्थान**: `runtime/logs/security.log`

**रिकॉर्ड सामग्री**:
- अटैक इंटरसेप्शन लॉग: अटैक श्रेणी, IP, पाथ, फ़ील्ड, स्रोत, payload खंड (पहले 200 वर्ण)

## 8. डेटा सुरक्षा

सिस्टम तीन-परत डेटा सुरक्षा नीति अपनाता है, जो डेटा प्रवाह के तीन चरणों के अनुरूप है।

### 8.1 ट्रांसमिशन परत — EncryptionService

`EncryptionService` `erikwang2013/encryption` पैकेज का उपयोग करता है, API रिक्वेस्ट/रिस्पॉन्स में संवेदनशील फ़ील्ड एन्क्रिप्ट/डिक्रिप्ट करता है।

**तकनीकी विवरण**:
- एल्गोरिदम: `aes-256-cbc-hmac` (अंतर्निहित HMAC सिग्नेचर, छेड़छाड़ रोकथाम)
- कुंजी: `ENCRYPTION_KEY` पर्यावरण चर, स्वचालित रूप से 32 बाइट पर अलाइन
- उपयोग: क्लाइंट और API के बीच फ़ोन नंबर, आईडी कार्ड नंबर आदि फ़ील्ड ट्रांसमिशन

**मास्किंग उपयोगिता मेथड**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (उपयोगकर्ता नाम 2 वर्ण से अधिक) या `a**@example.com`

### 8.2 स्टोरेज परत — Encryptable Cast

`AdminUser` मॉडल `Erikwang2013\Encryptable\Encryptable` Eloquent cast का उपयोग करता है, संबंधित फ़ील्ड:

- `email` → cast Encryptable, स्वचालित एन्क्रिप्शन/डिक्रिप्शन
- `phone` → cast Encryptable, स्वचालित एन्क्रिप्शन/डिक्रिप्शन
- `id_card` → cast Encryptable, स्वचालित एन्क्रिप्शन/डिक्रिप्शन

डेटाबेस में लिखते समय स्वचालित रूप से साइफरटेक्स्ट एन्क्रिप्ट होता है, पढ़ते समय स्वचालित रूप से प्लेनटेक्स्ट डिक्रिप्ट होता है। डेटाबेस स्टोरेज कॉलम प्रकार `VARCHAR(500)` है, साइफरटेक्स्ट base64 रूप में संग्रहीत।

**कुंजी प्रणाली**: ट्रांसमिशन परत एन्क्रिप्शन (`ENCRYPTION_KEY`) से स्वतंत्र रूप से `ENCRYPTABLE_KEY` उपयोग होता है; एक कुंजी लीक होने पर दूसरी परत विफल नहीं होती।

कुंजी रोटेशन: `ENCRYPTION_PREVIOUS_KEYS` पर्यावरण चर पुरानी कुंजियों की सूची (कॉमा-सेपरेटेड) समर्थित करता है; पुराना डेटा पढ़ते समय पुरानी कुंजियों से डिक्रिप्ट का प्रयास होता है, लिखते समय वर्तमान कुंजी से फिर से एन्क्रिप्ट होता है।

### 8.3 प्रदर्शन परत — ID ऑबफ़स्केशन और मास्किंग

**Hashids ID ऑबफ़स्केशन**: `HashidsService` `erikwang2013/hashids` पैकेज का उपयोग करता है।

- बाहरी API को लौटाई गई डेटाबेस BIGINT ID hash स्ट्रिंग में एन्कोड होती है (जैसे `xK3mN9qR2pL7wV8b`)
- क्लाइंट रिक्वेस्ट में hash स्ट्रिंग भेजता है, बैकएंड स्वचालित रूप से मूल ID में डिकोड करता है
- सॉल्ट मान `HASHIDS_SALT` पर्यावरण चर से इंजेक्ट होता है; सॉल्ट अलग होने पर एन्कोड/डिकोड परिणाम पूरी तरह अलग
- hash न्यूनतम लंबाई 16 अक्षर, 62-अक्षर अल्फ़ान्यूमेरिक कैरेक्टर सेट
- BaseController `encodeId()`, `decodeId()`, `encodeIds()` सुविधाजनक मेथड प्रदान करता है

**निर्यात मास्किंग**: Excel/PDF निर्यात के समय (ExportController), संवेदनशील फ़ील्ड एकीकृत रूप से मास्क होते हैं:
- फ़ोन नंबर: `138****1234`
- ईमेल: `a***@example.com`
- आईडी कार्ड: पूरी तरह `********` से ढका जाता है

## 9. कुंजी प्रबंधन

सभी कुंजियाँ `.env` पर्यावरण चर से इंजेक्ट होती हैं, कॉन्फ़िगरेशन फ़ाइलें `getenv()` से पढ़ती हैं और अंतर्निहित फॉलबैक डिफ़ॉल्ट मान रखती हैं (केवल विकास वातावरण के लिए सुरक्षित)।

| पर्यावरण चर | उपयोग | पैकेज | प्रोडक्शन आवश्यकता |
|----------|------|-----|---------|
| JWT_SECRET | JWT सिग्निंग कुंजी | erikwang2013/jwt-webman | 64+ वर्ण रैंडम स्ट्रिंग |
| JWT_ALGORITHM | JWT सिग्निंग एल्गोरिदम | वही | HS256 बनाए रखें |
| HASHIDS_SALT | ID एन्कोडिंग सॉल्ट मान | erikwang2013/hashids | रैंडम स्ट्रिंग |
| SNOWFLAKE_DATACENTER_ID | डेटासेंटर ID (0-31) | erikwang2013/snowflake-php | सिंगल डेटासेंटर में डिफ़ॉल्ट रखें |
| ENCRYPTION_KEY | API ट्रांसमिशन परत एन्क्रिप्शन कुंजी | erikwang2013/encryption | 32 बाइट रैंडम स्ट्रिंग |
| ENCRYPTABLE_KEY | DB स्टोरेज परत एन्क्रिप्शन कुंजी | erikwang2013/encryptable | 32 बाइट रैंडम स्ट्रिंग, ट्रांसमिशन कुंजी से अलग |

**सुरक्षा आवश्यकताएँ**:
- `.env` फ़ाइल `.gitignore` में जोड़ी गई है, वर्जन कंट्रोल में कमिट करना सख्त मना है
- `.env.example` सार्वजनिक टेम्पलेट फ़ाइल है, वास्तविक कुंजियाँ शामिल नहीं
- प्रोडक्शन में **अनिवार्य रूप से** सभी डिफ़ॉल्ट कुंजियों को रैंडम स्ट्रिंग से बदलें
- सुझाव: `openssl rand -base64 32` से कुंजियाँ जनरेट करें

### कुंजी स्टोरेज आइसोलेशन

| परत | कॉन्फ़िग कुंजी | कुंजी पर्यावरण चर |
|----|--------|-------------|
| ट्रांसमिशन एन्क्रिप्शन | `config/encryption.php` → `key` | `ENCRYPTION_KEY` |
| स्टोरेज एन्क्रिप्शन | `config/encryptable.php` → `key` | `ENCRYPTABLE_KEY` |
| ID ऑबफ़स्केशन | `config/hashids.php` → `connections.main.salt` | `HASHIDS_SALT` |
| JWT सिग्निंग | `config/plugin/erikwang2013/jwt/jwt` | `JWT_SECRET` |

## 10. security.txt (RFC 9116)

सिस्टम `/.well-known/security.txt` पर RFC 9116 मानक के अनुरूप सुरक्षा संपर्क जानकारी एंडपॉइंट प्रदान करता है, ताकि सुरक्षा शोधकर्ता कमज़ोरी खोजने पर रिपोर्ट चैनल तुरंत ढूंढ सकें।

**एक्सेस विधि**:

```
GET /.well-known/security.txt
```

**रिस्पॉन्स सामग्री**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**फ़ील्ड विवरण**:

| फ़ील्ड | विवरण |
|------|------|
| Contact | सुरक्षा कमज़ोरी रिपोर्ट संपर्क |
| Expires | फ़ाइल समाप्ति समय, नियमित अपडेट आवश्यक |
| Preferred-Languages | पसंदीदा संवाद भाषाएँ |
| Canonical | इस फ़ाइल का कैनोनिकल URL |
| Policy | सुरक्षा नीति/कमज़ोरी प्रकटीकरण नीति लिंक |

यह एंडपॉइंट रेट लिमिट, प्रमाणीकरण जैसे मिडलवेयर प्रतिबंधों से मुक्त है, कोई भी सीधे एक्सेस कर सकता है।

## 11. Nginx सुरक्षा कॉन्फ़िगरेशन

प्रोजेक्ट `docs/nginx-security.conf` को प्रोडक्शन वातावरण के Nginx रिवर्स प्रॉक्सी के सुरक्षा हार्डनिंग संदर्भ कॉन्फ़िगरेशन के रूप में प्रदान करता है।

**शामिल सुरक्षा उपाय**:

| कॉन्फ़िगरेशन आइटम | कार्य |
|--------|------|
| `server_tokens off` | Nginx संस्करण संख्या छिपाएँ |
| `client_max_body_size 10m` | रिक्वेस्ट बॉडी आकार सीमित, SecurityMiddleware (erikwang2013/security-php) के साथ समन्वय |
| `limit_req_zone` | Nginx स्तर पर रिक्वेस्ट फ़्रीक्वेंसी सीमा |
| `limit_conn_zone` | समवर्ती कनेक्शन संख्या सीमा |
| `add_header` सुरक्षा हेडर | Nginx स्तर पर X-XSS-Protection जैसे सुरक्षा हेडर जोड़ें |
| `if ($request_method)` | Nginx स्तर पर गैर-मानक HTTP मेथड अस्वीकार |
| SSL/TLS कॉन्फ़िगरेशन | आधुनिक TLS 1.2/1.3 कॉन्फ़िगरेशन, कमज़ोर सिफर सूट अक्षम |
| बैकएंड हेडर छिपाना | `proxy_hide_header` webman संस्करण जैसे संवेदनशील हेडर हटाता है |

**उपयोग विधि**: `docs/nginx-security.conf` में कॉन्फ़िगरेशन को अपने Nginx server ब्लॉक में मर्ज करें, वास्तविक डोमेन और सर्टिफिकेट पाथ के अनुसार समायोजित करें।

## 13. क्लाइंट पोर्टल और भुगतान सुरक्षा (M7–M10)
Stripe / PayPal वेबहुक सिग्नेचर जाँच (HMAC-SHA256 / verify-webhook-signature); भुगतान कुंजियाँ `Encryptable` से एन्क्रिप्ट कर `logistics_system_config` में; USDT TRC20 Tronscan से स्वचालित सत्यापन, BEP20 / ERC20 मैनुअल; X-API-Key क्लाइंट द्वारा सेट (≥16 अक्षर) sha256 रूप में संग्रहीत। गेटवे आक्रमण पहचान (M11): `ecat-security` SecurityBodyLayer गेटवे में एकीकृत, हमले के पेलोड गेटवे परत पर ही अवरुद्ध। **13.5 CDN सुरक्षा (M12)**: Cloudflare मुफ़्त प्लान पूर्ण HTTPS + द्वि-परत WAF (एज प्रबंधित नियम + गेटवे एप्लिकेशन परत जाँच); Tunnel ओरिजिन सोर्स शून्य एक्सपोज़र; कॉलबैक केवल DNS सबडोमेन सीधा कनेक्शन, CDN विफलता पर ऑर्डर न हारें; दर सीमा X-API-Key से गिनती, CDN एज IP से अप्रभावित; प्रमाणित एंडपॉइंट हमेशा no-store क्रॉस-यूज़र कैश मिक्सिंग रोकते हैं। **13.6 CDN प्रदाता कुंजी प्रबंधन (M13)**: CDN प्रदाता प्रोफ़ाइल (access_key / access_secret / डोमेन सूची) `logistics_cdn_provider` तालिका में, गोपनीय फ़ील्ड `Encryptable` से एन्क्रिप्ट, `/admin/cdn/provider` CRUD से प्रबंधन।
