## 1. بانوراما الدفاع المتعمق

يعتمد النظام نموذج دفاع متعمق من 7 طبقات، تصفّي الطلبات الخبيثة طبقة تلو الأخرى من الخارج إلى الداخل، لضمان بقاء خطوط دفاع لاحقة حتى عند تعطل أي طبقة منفردة.

تُنفَّذ سلسلة الوسائط بأكملها بالترتيب التالي (راجع `config/middleware.php`):

```
请求 → Cors → Locale(Accept-Language) → SecurityMiddleware (erikwang2013/security-php, 31种检测器) → RateLimit → [路由组中间件: AdminAuth → AdminPermission → OperationLog] → Controller
```

| الطبقة | الوسيط/الآلية | هدف الحماية |
|----|--------|---------|
| 1 | SecurityMiddleware (erikwang2013/security-php) | 31 نوع كشف هجوم + التحقق من طرق HTTP + حد حجم جسم الطلب + التحقق من Content-Type + CSRF + قائمة سوداء لتصعيد هجمات IP |
| 2 | Cors | أمان مشاركة الموارد عبر النطاقات + حقن ترويسات الأمان في الاستجابات |
| 3 | RateLimit | تحديد معدل Redis بنافذة منزلقة، ضد القوة الغاشمة |
| 4 | AdminAuth | مصادقة JWT + تسجيل الخروج عبر القائمة السوداء |
| 5 | AdminPermission | تحقق صلاحيات RBAC بدقة method.path |
| 6 | OperationLog | تدقيق العمليات + تتبع جهة المصدر |
| 7 | تشفير البيانات | إخفاء معرفات Hashids + تشفير قاعدة البيانات عبر Encryptable + تشفير النقل عبر EncryptionService |

تمتلك الواجهة الأمامية ذات الطبقات الثلاث (Flutter) تحققًا مستقلًا من المدخلات، ولا يثق الخادم في الواجهة الأمامية، فكل طبقة تدافع بشكل مستقل.

## 2. محرك كشف الهجمات

## 2. محرك كشف الهجمات (erikwang2013/security-php)

انتقل كشف الهجمات من SecurityMiddleware ذاتي التطوير إلى الحزمة الأمنية المتخصصة `erikwang2013/security-php` v1.1+، التي توفر **31 نوع كاشف** تغطي 5 فئات هجوم كبرى.

### 2.1 تصنيف الكواشف

**هجمات الحقن (11 نوعًا):** XSS، حقن SQL، حقن الأوامر، حقن NoSQL، حقن LDAP، حقن XPath، JNDI/Log4Shell، SSI تضمين الخادم، حقن GraphQL، حقن قوالب SSTI

**هجمات البروتوكول والطلبات (9 أنواع):** SSRF، XXE، حقن ترويسات استجابة HTTP، هجوم ترويسة Host، Request Smuggling، Open Redirect، تجاوز CORS، اختطاف WebSocket، DNS Rebinding

**التحقق على مستوى بروتوكول HTTP (6 أنواع):** التحقق من طرق HTTP(405)، حد حجم جسم الطلب(413)، التحقق من Content-Type(415)، فحص أصل CSRF، القائمة السوداء لتصعيد هجمات IP، كشف تسريب البيانات الحساسة

**هجمات البيانات والتسلسل (5 أنواع):** إلغاء تسلسل PHP، حقن صيغ CSV، حقن ترويسات البريد، هجمات JWT (تحليل بنيوي)، JS Prototype Pollution

**هجمات الملفات والمسارات (نوعان):** اجتياز المسار، رفع ملفات خبيثة

### 2.2 أوضاع المعالجة

يدعم كل كاشف وضعين بشكل مستقل:
- `block` — اعتراض فوري عند اكتشاف هجوم، مع إرجاع رمز الحالة المكوَّن
- `log` — تسجيل في السجلات فقط دون اعتراض (`header_injection` و`ssti` و`nosql_injection` افتراضيًا بوضع log لمنع النتائج الإيجابية الكاذبة)

### 2.3 القائمة السوداء لتصعيد هجمات IP

نفس IP الذي يفعّل 5 كشوفات هجوم خلال 60 ثانية → يُحظر تلقائيًا لمدة 15 دقيقة. خلفية التخزين اختيارية: Redis (موزع) أو File (JSON أحادي الجهاز) أو Cache (ملف مستقل عالي التزامن)، والإعداد الحالي هو تخزين Redis.

### 2.4 سجلات الأمان

موقع الملف: `runtime/logs/security.log` (تدوير تلقائي، 10MB/ملف)

## 4. ترويسات أمان الاستجابة

تُحقن جميع الترويسات في وسيط `Cors`، وتُضاف إلى كل استجابة عبر `$response->withHeaders()`.

| الترويسة | القيمة | الوظيفة |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | السماح بالوصول عبر النطاقات من أي مصدر (سيناريو لوحة الإدارة الداخلية) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | مجموعة الطرق المسموحة |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | الترويسات المخصصة المسموحة |
| Access-Control-Max-Age | `86400` | تخزين طلب الفحص المسبق مؤقتًا لمدة 24 ساعة |
| X-Content-Type-Options | `nosniff` | منع المتصفح من فحص MIME |
| X-Frame-Options | `DENY` | منع كل تضمين iframe، ضد اختطاف النقر |
| X-XSS-Protection | `1; mode=block` | تفعيل مرشح XSS المدمج في المتصفح واعتراض عرض الصفحة |
| Referrer-Policy | `strict-origin-when-cross-origin` | نفس المصدر يرسل URL كاملاً، عبر النطاقات يرسل النطاق فقط |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | تعطيل واجهات الكاميرا/الميكروفون/تحديد الموقع في الموقع بالكامل |

تُرجع طلبات الفحص المسبق OPTIONS استجابة 204 فارغة مباشرة، دون الدخول في سلسلة الوسائط اللاحقة.

### 4.2 Content-Security-Policy (CSP)

تُحقن مع ترويسات الأمان الأخرى في وسيط Cors، لتوفير دفاع متعمق يقيّد مصادر الموارد التي يمكن للمتصفح تحميلها وتنفيذها.

| الترويسة | القيمة | الوظيفة |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | تقييد مصادر السكربتات/الأنماط/الصور/الاتصالات/الأطر/النماذج وغيرها |
| X-Permitted-Cross-Domain-Policies | `none` | منع تحميل ملفات السياسات عبر النطاقات من Adobe Flash/PDF وغيرها |

نقاط سياسة CSP الأساسية:
- `default-src 'self'`: افتراضيًا يُسمح فقط بمصادر نفس الأصل
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: السماح بسكربتات نفس الأصل + السكربتات المضمّنة (ضرورية لـ Flutter Web) + eval (ضرورية لتصحيح أخطاء Flutter Web)
- `frame-ancestors 'none'`: منع تضمين الصفحة في أي iframe، حماية مزدوجة مع X-Frame-Options: DENY
- `base-uri 'self'`: تقييد وسم `<base>` ليشير إلى نفس الأصل فقط
- `form-action 'self'`: تقييد النماذج للإرسال إلى نفس الأصل فقط

## 5. استراتيجية تحديد المعدل

### الخوارزمية

نافذة منزلقة عبر Redis Sorted Set + سكربت Lua ذرّي، للعمليات الحرجة:

```lua
-- 1. 清理窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. 检查当前窗口计数
local count = redis.call('ZCARD', KEYS[1])
-- 3. 超限则返回 {0, count}，未超限则 ZADD 并返回 {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- 随机后缀避免同毫秒覆盖
redis.call('EXPIRE', KEYS[1], window + 10)
```

يُنفَّذ سكربت Lua بخيط واحد على الخادم في Redis، وهو **ذرّي بطبيعته**، مما يزيل شروط السباق TOCTOU (Time-of-check to Time-of-use).

### إعدادات تحديد المعدل

| المسار | الحد | النافذة | السيناريو |
|------|------|------|------|
| الافتراضي (جميع المسارات) | 60 مرة/دقيقة | 60s | API عام |
| `/api/auth/login` | 10 مرات/دقيقة | 60s | تسجيل الدخول (ضد القوة الغاشمة) |
| `/api/auth/register` | 5 مرات/دقيقة | 60s | التسجيل (ضد التسجيل الجماعي) |

### ترويسات الاستجابة

عند تفعيل تحديد المعدل يُرجع HTTP 429 مع جسم JSON:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

تحمل جميع الاستجابات (بما فيها العادية) الترويسات التالية:

| الترويسة | الوصف |
|----|------|
| X-RateLimit-Limit | الحد الأقصى للطلبات المسموح بها في النافذة الحالية |
| X-RateLimit-Remaining | عدد الطلبات المتبقية المتاحة في النافذة الحالية |
| X-RateLimit-Reset | طابع Unix لإعادة تعيين النافذة |
| Retry-After | تُرسل فقط عند تفعيل تحديد المعدل، عدد الثواني الموصى بالانتظار |

### استراتيجية التدهور

عند شذوذ Redis (انتهاء مهلة الاتصال، عدم التوفر...) يُفعَّل **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis down, 放行所有请求
}
```

من الأفضل فقدان حماية تحديد المعدل مؤقتًا بدلًا من حجب طلبات الأعمال العادية.

### 5.4 آلية قفل الحساب

بالإضافة إلى تحديد المعدل، تضيف واجهة الدخول آلية **قفل الحساب** لمنع القوة الغاشمة الموجهة ضد مستخدمين محددين.

**عملية القفل**:

```
登录失败 → Redis INCR account_lockout:{userId} TTL=900s
连续 5 次失败 → Redis SETEX account_locked:{userId} 900 1
            → 返回 429 "账号已被锁定，请15分钟后再试"
            → 清除计数器 DEL account_lockout:{userId}
```

**السلوك أثناء القفل**:

تُرجع جميع طلبات الدخول خلال فترة القفل 429 مباشرة دون التحقق من كلمة المرور، مما يمنع محاولات القوة الغاشمة تمامًا.

**ثوابت الإعداد**:

| الثابت | القيمة | المعنى |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | الحد الأقصى لمرات الفشل المتتالية |
| LOCKOUT_DURATION | 900 | مدة القفل (بالثواني)، أي 15 دقيقة |

ملاحظة: يعتمد قفل الحساب على `userId` وليس IP، فلا يمكن للمهاجم تجاوز القفل بتغيير IP. وبتكامله مع تحديد معدل IP (10 مرات/دقيقة) تتشكل حماية مزدوجة:
- على مستوى IP: تحديد المعدل 10 مرات/دقيقة يمنع القوة الغاشمة الموزعة
- على مستوى الحساب: القفل بعد 5 محاولات فاشلة يمنع القوة الغاشمة الموجهة

## 6. المصادقة والتفويض

### 6.1 مصادقة JWT

تنفذها وسيط AdminAuth، مركّبة على مجموعات المسارات التي تتطلب المصادقة.

**إعدادات المعاملات** (`config/plugin/erikwang2013/jwt/jwt`، تُحقن عبر `.env`):

| المعامل | القيمة | الوصف |
|------|-----|------|
| الخوارزمية | HS256 | توقيع متماثل HMAC-SHA256 |
| المفتاح | `JWT_SECRET` | يُحقن عبر متغير بيئة، يجب تغييره في الإنتاج |
| صلاحية access_token | 7200s (2h) | `JWT_TTL` |
| صلاحية refresh_token | 1209600s (14d) | `JWT_REFRESH_TTL` |
| المُصدِر | `open-admin` | `JWT_ISSUER` |
| الجمهور | `open-admin` | `JWT_AUDIENCE` |

**استخراج الرمز**: يُستخرج من ترويسة `Authorization: Bearer <token>`، ويُحذف مسبوقة `Bearer ` للحصول على JWT الأصلي.

**عملية المصادقة**:
1. رمز فارغ → 401 مباشرة `{"code": 401, "message": "未登录"}`
2. فحص القائمة السوداء في Redis `jwt_blacklist:{md5(token)}` → إصابة → 401 `Token已失效，请重新登录`
3. فك ترميز JWT → فشل (منتهي/توقيع غير مطابق) → 401 `Token已过期或无效`
4. نجاح → حقن `$request->adminId` و`$request->adminUsername`

**آلية القائمة السوداء**: عند تسجيل خروج المستخدم، يُكتب `md5(token)` في Redis مع TTL يساوي الصلاحية المتبقية لـ JWT. عند تعطل Redis يُتخطى فحص القائمة السوداء (fail-open)، ويمكن وقتها استخدام الرمز المسجل خروجه لفترة قصيرة، لكن الصلاحية القصيرة لـ JWT نفسها (2h) تبقى حماية أساسية.

### 6.2 حد الجلسات المتزامنة

لمنع إساءة استخدام الرمز المسرَّب على أجهزة متعددة، يحدّ النظام عدد الرموز الصالحة التي يحملها نفس المستخدم في الوقت نفسه.

**منطق التحديد**:

```
登录成功 → 签发新 Token
         → 查询当前用户有效 Token 数量: Redis SCARD user_tokens:{userId}
         → 若数量 >= 3（MAX_CONCURRENT_SESSIONS）:
            → 按创建时间升序排列，移除最旧的 Token:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → 将新 Token 加入集合: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**ثوابت الإعداد**:

| الثابت | القيمة | المعنى |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | الحد الأقصى للرموز المتزامنة لنفس المستخدم |

**سيناريو الطرد**: عند دخول المستخدم من الجهاز الرابع، يُضاف رمز الجهاز الأول قسريًا إلى القائمة السوداء، وتُرجع طلباته اللاحقة 401 "Token已失效，请重新登录".

عند تسجيل الخروج يُزال الرمز الحالي من المجموعة. وعند انتهاء صلاحية الرمز طبيعيًا، يبطل مفتاح Redis تلقائيًا وتتناقص عناصر المجموعة تبعًا لذلك.

### 6.3 نموذج صلاحيات RBAC

تنفذه وسيط AdminPermission.

**نموذج البيانات**: ارتباط ثلاثي المستويات User -> Role -> Permission

- `erik_admin_user` (جدول المستخدمين)
- `erik_admin_user_role` (جدول ارتباط المستخدمين-الأدوار)
- `erik_admin_role` (جدول الأدوار)
- `erik_admin_role_permission` (جدول ارتباط الأدوار-الصلاحيات)
- `erik_admin_permission` (جدول الصلاحيات)

**أنواع الصلاحيات**:
| type | المعنى | مثال |
|------|------|------|
| 1 | صلاحية قائمة | التحكم في ظهور التنقل الجانبي |
| 2 | صلاحية زر | التحكم في أزرار العمليات داخل الصفحة (إضافة/تعديل/حذف) |
| 3 | صلاحية API | التحكم في استدعاء واجهات الخادم |

تنسيق معرّف صلاحية API: `{method}.{path}`

مثال:
- `post.admin/user` — إنشاء مستخدم
- `put.admin/user` — تعديل مستخدم
- `delete.admin/user` — حذف مستخدم
- `get.admin/user` — عرض قائمة المستخدمين

**عملية التحقق**:
1. `$request->adminId` فارغ → تمرير (المسار لم يهيّئ مصادقة مسبقة)
2. الحصول على المستخدم → الأدوار (تخطي الأدوار المعطلة `status=0`) → قائمة الصلاحيات
3. المدير الفائق (`slug = '*'`) → تمرير مباشر
4. بناء `strtolower(method) . '.' . trim(path, '/')` → مقارنة بقائمة الصلاحيات
5. عدم تطابق → 403 `{"code": 403, "message": "无权限访问"}`

**التأكيد الثاني**: يوفّر BaseController دالة `confirmPassword()`، وتتطلب العمليات الحساسة (حذف المستخدمين، تصدير البيانات وغيرها) إدخال كلمة المرور الحالية إضافيًا في طبقة وحدات التحكم، لمنع العمليات غير المصرح بها بعد اختطاف الجلسة.

## 7. سجلات التدقيق

### 7.1 سجلات العمليات

يسجّل وسيط OperationLog سجلات العمليات تلقائيًا لطلبات POST / PUT / DELETE. ولا تُسجَّل طلبات GET.

**الحقول المسجَّلة**:

| الحقل | المصدر | الوصف |
|------|------|------|
| id | SnowflakeService::generate() | معرف فريد عالميًا |
| user_id | `$request->adminId` | معرف الفاعل، 0 عند عدم تسجيل الدخول |
| action | `$request->method()` | يكافئ method |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | مسار الطلب |
| ip | `$request->getRealIp()` | عنوان IP الحقيقي للعميل |
| source | detectSource() | منصة مصدر العميل |
| input | جسم الطلب (JSON بعد الإخفاء) | البيانات المقدمة للعملية |
| created_at | `date('Y-m-d H:i:s')` | وقت العملية |

**فلترة الحقول الحساسة**: تُجتاز حقول الجسم تكراريًا، وتُستبدل قيم الحقول التالية بـ `***`:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**كشف جهة المصدر** (`detectSource()`): حسب الأولوية:

1. قراءة الترويسة المخصصة `X-Client-Platform` أولًا (تصريح صريح من العميل الأصلي)
2. التدهور إلى الاستنتاج من سلسلة User-Agent (ترتيب كشف دالة `detectSource()`):

| المنصة | كلمات UA الرئيسية |
|------|----------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | القيمة الافتراضية الاحتياطية |

**تحمل الأخطاء**: لا تعيق أخطاء كتابة السجلات طلبات الأعمال (تُبتلع بصمت عبر `catch (\Throwable)`).

### 7.2 سجلات الأمان

**موقع الملف**: `runtime/logs/security.log`

**المحتوى المسجَّل**:
- سجلات اعتراض الهجمات: فئة الهجوم، IP، المسار، الحقل، المصدر، مقتطف payload (أول 200 حرف)
- إشعارات حظر IP: IP المحظور، عدد مرات التفعيل

صلاحيات السجل `FILE_APPEND | LOCK_EX` لضمان الكتابة الآمنة المتزامنة.

## 8. حماية البيانات

يعتمد النظام استراتيجية حماية بيانات من ثلاث طبقات، تقابل المراحل الثلاث لتدفق البيانات.

### 8.1 طبقة النقل — EncryptionService

يستخدم `EncryptionService` حزمة `erikwang2013/encryption` لتشفير وفك تشفير الحقول الحساسة في طلبات/استجابات API.

**التفاصيل التقنية**:
- الخوارزمية: `aes-256-cbc-hmac` (تتضمن توقيع HMAC مضادًا للعبث)
- المفتاح: متغير البيئة `ENCRYPTION_KEY`، يُضبط تلقائيًا على 32 بايت
- الاستخدام: نقل حقول مثل رقم الهاتف ورقم الهوية بين العميل وAPI

**دوال أدوات الإخفاء**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (اسم المستخدم أكثر من حرفين) أو `a**@example.com`

### 8.2 طبقة التخزين — Encryptable Cast

يستخدم نموذج `AdminUser` تحويل Eloquent `Erikwang2013\Encryptable\Encryptable`، والحقول المقابلة:

- `email` → cast إلى Encryptable، تشفير وفك تشفير تلقائي
- `phone` → cast إلى Encryptable، تشفير وفك تشفير تلقائي
- `id_card` → cast إلى Encryptable، تشفير وفك تشفير تلقائي

يُشفَّر تلقائيًا إلى نص مشفر عند الكتابة في قاعدة البيانات، ويُفك تشفيره تلقائيًا عند القراءة. نوع عمود التخزين في قاعدة البيانات هو `VARCHAR(500)`، ويُخزَّن النص المشفر بصيغة base64.

**نظام المفاتيح**: يستخدم مفتاح `ENCRYPTABLE_KEY` مستقلًا عن تشفير طبقة النقل (`ENCRYPTION_KEY`)، فلا يؤدي تسريب أحد المفاتيح إلى تعطل الطبقة الأخرى.

تدوير المفاتيح: يدعم متغير البيئة `ENCRYPTION_PREVIOUS_KEYS` قائمة مفاتيح تاريخية (مفصولة بفواصل)، فيُحاول فك تشفير البيانات القديمة بالمفاتيح التاريخية عند القراءة، ويعيد تشفيرها بالمفتاح الحالي عند الكتابة.

### 8.3 طبقة العرض — إخفاء المعرفات والإخفاء

**إخفاء معرفات Hashids**: يستخدم `HashidsService` حزمة `erikwang2013/hashids`.

- تُرمَّز معرفات BIGINT لقاعدة البيانات التي تُرجعها واجهات API الخارجية إلى سلاسل hash (مثل `xK3mN9qR2pL7wV8b`)
- يمرر العميل سلسلة hash عند الطلب، ويفك الخادم ترميزها تلقائيًا إلى المعرف الأصلي
- يُحقن الملح عبر متغير البيئة `HASHIDS_SALT`، وتختلف نتائج الترميز وفك الترميز تمامًا باختلاف الملح
- الحد الأدنى لطول hash 16 خانة، باستخدام مجموعة أحرف أبجدية رقمية من 62 رمزًا
- يوفّر BaseController دوال ملائمة: `encodeId()` و`decodeId()` و`encodeIds()`

**إخفاء التصدير**: عند تصدير Excel/PDF (عبر ExportController)، تُخفى الحقول الحساسة بشكل موحد:
- رقم الهاتف: `138****1234`
- البريد الإلكتروني: `a***@example.com`
- رقم الهوية: تغطية كاملة بـ `********`

## 9. إدارة المفاتيح

| ENCRYPTABLE_KEY | مفتاح تشفير طبقة تخزين DB | erikwang2013/encryptable | سلسلة عشوائية من 32 بايت، مختلفة عن مفتاح النقل |

- في بيئة الإنتاج **يجب** استبدال جميع المفاتيح الافتراضية بسلاسل عشوائية
- يُوصى بتوليد المفاتيح عبر `openssl rand -base64 32`

## 10. security.txt (RFC 9116)

يوفر النظام نقطة معلومات الاتصال الأمني المتوافقة مع معيار RFC 9116 في `/.well-known/security.txt`، لتسهيل وصول باحثي الأمان إلى قناة الإبلاغ بسرعة عند اكتشاف ثغرات.

**طريقة الوصول**:

```
GET /.well-known/security.txt
```

**محتوى الاستجابة**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**شرح الحقول**:

| الحقل | الوصف |
|------|------|
| Contact | وسيلة الإبلاغ عن الثغرات الأمنية |
| Expires | وقت انتهاء الملف، يحتاج تحديثًا دوريًا |
| Preferred-Languages | لغات التواصل المفضلة |
| Canonical | عنوان URL الرسمي لهذا الملف |
| Policy | رابط سياسة الأمان/سياسة كشف الثغرات |

لا تخضع هذه النقطة لوسائط تحديد المعدل أو المصادقة، ويمكن لأي شخص الوصول إليها مباشرة.

## 11. إعدادات أمان Nginx

يوفر المشروع `docs/nginx-security.conf` كمرجع لإعدادات تحصين أمان الوكيل العكسي في بيئة الإنتاج.

**الإجراءات الأمنية المتضمنة**:

| عنصر الإعداد | الوظيفة |
|--------|------|
| `server_tokens off` | إخفاء رقم إصدار Nginx |
| `client_max_body_size 10m` | تقييد حجم جسم الطلب، بالتكامل مع SecurityMiddleware (erikwang2013/security-php) |
| `limit_req_zone` | تحديد تردد الطلبات على مستوى Nginx |
| `limit_conn_zone` | تقييد عدد الاتصالات المتزامنة |
| ترويسات `add_header` الأمنية | إضافة ترويسات أمان مثل X-XSS-Protection على مستوى Nginx |
| `if ($request_method)` | رفض طرق HTTP غير القياسية على مستوى Nginx |
| إعدادات SSL/TLS | إعدادات TLS 1.2/1.3 حديثة، تعطيل حزم التشفير الضعيفة |
| إخفاء ترويسات الخلفية | `proxy_hide_header` لإزالة الترويسات الحساسة مثل إصدار webman |

**طريقة الاستخدام**: ادمج إعدادات `docs/nginx-security.conf` في كتلة server الخاصة بـ Nginx، واضبطها حسب النطاق الفعلي ومسارات الشهادات.
