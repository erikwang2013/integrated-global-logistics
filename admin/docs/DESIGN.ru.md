## 2. Архитектура бэкенда

### 2.1 Многослойный дизайн

| Слой | Каталог | Обязанности |
|---|------|------|
| Маршрутизация | `config/route.php` | Сопоставление URL с контроллерами, привязка промежуточного ПО, версионированные маршруты |
| Промежуточное ПО | `app/middleware/` | Перехват атак (SecurityFilter), лимит запросов (RateLimit), аутентификация (JWT), авторизация (RBAC), версия API (ApiVersion) |
| Контроллеры | 14: Dashboard/User/Role/Permission/Config/Log/Profile/Export/Import/Upload/Health/Docs (админка) + Captcha/Auth (API v1) | Валидация параметров запроса, вызов бизнес-логики, форматирование ответов |
| Бизнес-сервисы | `app/service/` | Переиспользуемая бизнес-логика (зарезервировано) |
| Модели данных | `app/model/` | ORM-отображение, связи, шифрование полей |
| Общие утилиты | `app/common/` | Сервисы Hashids, Snowflake, Encryption |

### 2.2 Жизненный цикл запроса

```
客户端请求
  │
  ▼
webman HTTP Server (workerman)
  │
  ▼
Route 匹配
  │
  ▼
中间件链:
  Locale ──────────────► Accept-Language / ?lang= 语言检测
  │
  ▼
  SecurityFilter ──────► HTTP方法检查 → 405 (仅允许 GET/POST/PUT/DELETE/OPTIONS/HEAD)
  │                     XSS/SQL注入/路径遍历/命令注入/CSRF 攻击拦截 (403)
  ▼
  RateLimit ───────────► Redis 滑动窗口限流
  │ (失败返回 429 + Retry-After 头)
  ▼
  ApiVersion ─────────► API-Version 头校验，注入 $request->apiVersion
  │ (失败返回 400)
  ▼
  AdminAuth ──────────► JWT 验证，注入 $request->adminId
  │ (失败返回 401)
  ▼
  AdminPermission ────► RBAC 权限校验（Redis 60s 缓存）
  │ (失败返回 403)
  ▼
  OperationLog ───────► 操作日志记录 (POST/PUT/DELETE)，自动检测来源端
  │
  ▼
Controller::method()
  │
  ├─► 参数验证 (validator)
  ├─► 敏感操作确认 (confirmPassword)
  ├─► decodeId() — hashid → BIGINT
  ├─► Model 操作 (自动 encryptable 加解密)
  ├─► encodeId() — BIGINT → hashid
  └─► Response JSON
```

### 2.3 Жизненный цикл ID

```
生成 (Snowflake) → 存储 (MySQL BIGINT) → 传输 (Hashids 编码) → 外部 (hash 字符串)
                                                                    │
                            HashidsService::decode() ←──────────────┘
```

### 2.4 Система шифрования данных

```
传输层 (encryption)     — AES-256-CBC，独立密钥
存储层 (encryptable)    — AES-128-ECB，独立密钥，Model $casts 自动处理
展示层 (mask)           — 手机号: 138****1234，邮箱: a***@example.com
```

### 4.2 Стратегия версионирования API

Версия API задаётся заголовком запроса и **не отражается в пути URL**:

```http
API-Version: v1
```

| Механизм | Описание |
|------|------|
| Версия по умолчанию | При отсутствии заголовка `API-Version` по умолчанию `v1` |
| Проверка | Middleware `ApiVersion` проверяет; неподдерживаемая версия возвращает 400 |
| Маршрутизация | Вспомогательная функция `v()` динамически резолвит класс контроллера по версии |
| Каталог | Контроллеры организованы по версиям: `app/api/{version}/controller/` |

Пример расширения — добавление API v2:
1. Создайте `app/api/v2/controller/AuthController.php`
2. В middleware `ApiVersion` добавьте `'v2'` в константу `SUPPORTED`
3. Определения маршрутов менять не нужно

```bash
# Использование v1
curl -H "API-Version: v1" /api/auth/login

# Использование v2
curl -H "API-Version: v2" /api/auth/login

# Без заголовка — по умолчанию v1
curl /api/auth/login
```

### 4.3 Политика лимитов запросов

Алгоритм скользящего окна на базе Redis Sorted Set, атомарное исполнение через Lua-скрипт:

| Интерфейс | Лимит |
|------|------|
| По умолчанию | 60 раз/мин/IP/маршрут |
| POST /api/auth/login | 10 раз/мин |
| POST /api/auth/register | 5 раз/мин |

При превышении возвращается 429, заголовки ответа содержат X-RateLimit-Limit / Remaining / Reset / Retry-After.

### 4.4 Единый формат ответа

```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

| code | Значение | Сценарий возникновения |
|------|------|---------|
| 0 | Успех | Нормальный ответ |
| 400 | Ошибка параметров | Некорректный формат запроса |
| 401 | Не аутентифицирован | Token отсутствует/истёк/недействителен |
| 403 | Нет прав | Роль пользователя не содержит требуемого права |
| 404 | Не найдено | Ресурс не найден |
| 422 | Ошибка валидации | Параметры формы не соответствуют правилам / ошибка подтверждения пароля |
| 500 | Ошибка сервера | Непредвиденное исключение |

### 4.5 Процесс аутентификации (с капчей по клику)

```
客户端                               服务端
  │                                    │
  │  ① POST /api/captcha/generate     │ captcha_create('click')
  │◄── {key, image(base64), targets}  │
  │                                    │
  │  ② 用户点击图中文字位置              │
  │                                    │
  │  ③ POST /api/auth/login           │
  │     {username, password,          │
  │      captcha_key, clicks}         │
  │────────────────────────────────►  │
  │                                    │ ① captcha_verify()
  │                                    │ ② password_verify()
  │                                    │ ③ jwt()->create()
  │◄── {access_token, refresh_token}  │
  │                                    │
  │  ④ GET /admin/dashboard           │
  │     Authorization: Bearer xxx     │
  │────────────────────────────────►  │ AdminAuth → AdminPermission
  │◄── 200 {dashboard data}           │
```

### 4.6 Модель прав (RBAC)

```
  用户 ──┬── 角色 ──┬── 权限
  User     Role      Permission
                 │
                 ├── type=1: 菜单 (控制侧边栏可见)
                 ├── type=2: 按钮 (控制页面内操作)
                 └── type=3: API  (控制接口访问)

  权限标识格式: {method}.{path}
  例: get.admin/user  post.admin/user  delete.admin/user
  超级管理员标识: * (跳过所有权限检查)
```

### 4.7 Повторное подтверждение чувствительных операций

Чувствительные операции, такие как удаление пользователя, роли или права, требуют передачи пароля текущего пользователя в теле запроса для повторной проверки личности:

```
客户端                           服务端
  │                                │
  │  DELETE /admin/user/{hashid}  │
  │  { password: "******" }       │
  │────────────────────────────►  │
  │                                │ confirmPassword(adminId, password)
  │                                │ → 密码错误返回 422
  │                                │ → 密码正确继续执行
  │◄── 200 { code: 0 }           │
```

Фронтенд перед запуском операции удаления показывает диалог подтверждения, собирает пароль пользователя и отправляет запрос.

## 6. Дизайн безопасности

### 6.1 Эшелонированная оборона

| Слой | Меры |
|------|------|
| Ограничение методов | SecurityFilter: белый список HTTP-методов, только GET/POST/PUT/DELETE/OPTIONS/HEAD, нестандартные методы — 405 |
| Перехват атак | Middleware SecurityFilter: обнаружение и блокировка XSS/SQL-инъекций/обхода путей/инъекций команд/CSRF |
| Человек-машина | Капча по клику (Click Captcha), обязательна при входе/регистрации |
| Блокировка учётной записи | 5 неудачных входов подряд — блокировка на 15 минут, в этот период — 429 |
| Ограничение сессий | Не более 3 одновременных Token на пользователя; самый старый Token автоматически в чёрный список |
| Лимит запросов | Middleware RateLimit, скользящее окно Redis, атомарный Lua |
| CSP | Заголовок Content-Security-Policy ограничивает источники ресурсов, защита от XSS и инъекций данных |
| Подтверждение операций | Чувствительные операции (удаление и т. п.) требуют повторного ввода пароля текущего пользователя |
| Передача | HTTPS + JWT Bearer Token |
| ID в API | Шифрование Hashids, реальный ID невозможно вычислить извне |
| Тело запроса | Шифрование чувствительных полей AES-256-CBC |
| База данных | BIGINT-первичные ключи (не раскрывают автоинкремент) |
| База данных | Хранение чувствительных полей в шифрованном виде AES-128-ECB |
| Аутентификация | JWT HS256, истечение 2h + refresh token |
| Авторизация | RBAC, управление правами с точностью method.path |
| Аудит | OperationLog записывает все операции (включая автоматическое определение источника `source`) |

### 6.2 Управление ключами

```
JWT_SECRET          → 环境变量注入，64位随机字符串
HASHIDS_SALT        → 唯一盐值，泄漏后需全局更换
ENCRYPTION_KEY      → API 传输加密密钥，32字节
ENCRYPTABLE_KEY     → DB 存储加密密钥，与传输密钥独立
SCOUT_HOSTS         → ES 地址，内网部署
```

### 6.3 Защита чувствительных данных

| Сценарий | Поле | Меры |
|------|------|------|
| Отображение в списке | phone | Маскирование: 138****1234 |
| Отображение в списке | email | Маскирование: a***@example.com |
| Просмотр деталей | phone/email | Требуется интерфейс расшифровки |

| Хранение | phone/email/id_card | encryptable шифрует в шифротекст |

| `nginx` | nginx:alpine | 80, 443 | Обратный прокси + статические файлы + Gzip |
| `app` | локальная сборка из `Dockerfile` | 8787 | PHP 8.3 + OPcache + webman |

Перед запуском замените ключи `JWT_SECRET`, `HASHIDS_SALT`, `ENCRYPTION_KEY` в `docker-compose.yml` на случайные строки.

```bash
cp .env.docker .env
docker-compose up -d
```

### 8.3 CI/CD

Непрерывная интеграция GitHub Actions определена в `.github/workflows/ci.yml`:
- Синтаксическая проверка PHP (`php -l`)
- Модульные тесты PHPUnit
- Статический анализ Flutter (`flutter analyze`)

### 8.4 Резервное копирование БД

`database/backup/backup.sh` — резервное копирование mysqldump + gzip, автоматическая очистка бэкапов старше 30 дней.
`database/backup/restore.sh` — интерактивный выбор и восстановление бэкапа.

### 8.5 Мониторинг

Эндпоинт `GET /metrics` (`MetricsController`) в формате Prometheus text format раскрывает 5 метрик gauge: общее число HTTP-запросов, число активных пользователей, состояние соединений БД/Redis, потребление памяти.
